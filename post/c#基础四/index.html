一、什么是内聚性和耦合性

✅面试简答（考场口述答案）

**内聚性（Cohesion）和耦合性（Coupling）是衡量软件模块设计质量的两个核心指标，通常遵循“高内聚、低耦合”**的设计原则。

  • 内聚性：指一个模块内部各个元素（方法、属性）之间结合的紧密程度。高内聚意味着模块只负责单一、明确的功能，职责清晰。
  • 耦合性：指不同模块之间相互依赖的程度。低耦合意味着模块之间联系松散，修改一个模块不会轻易影响其他模块。

目标是：让模块内部紧密相关，模块之间尽可能独立。

📚深入解析

1. 内聚性（Cohesion）：从低到高

内聚性越高，模块的可维护性和复用性越好。常见的内聚类型（由低到高）：

类型 描述 评价
偶然内聚 模块内的任务毫无逻辑联系，只是凑在一起 ❌ 极差
逻辑内聚 完成逻辑上相似但功能不同的任务（如一个类处理所有输入） ❌ 差
时间内聚 任务仅在时间上相关（如初始化模块，包含打开文件、连接DB等） ⚠️ 一般
过程内聚 任务按特定顺序执行，前一个输出是后一个输入 ⚠️ 一般
通信内聚 模块内所有操作都使用相同的数据 ✅ 良好
顺序内聚 模块内的处理元素相关，且必须依次执行 ✅ 良好
功能内聚 模块内所有元素共同完成一个单一功能 🏆 最佳

面试重点：现代开发追求的单一职责原则（SRP）本质上就是追求功能内聚。

2. 耦合性（Coupling）：从高到低

耦合性越低，系统的灵活性和可测试性越强。常见的耦合类型（由高到低）：

类型 描述 评价
内容耦合 一个模块直接修改另一个模块的内部数据 ❌ 极差
公共耦合 多个模块共享同一个全局变量 ❌ 差
外部耦合 模块依赖于外部环境格式（如硬编码的文件路径、协议） ⚠️ 一般
控制耦合 一个模块通过传递标志位来控制另一个模块的逻辑分支 ⚠️ 一般
标记耦合 模块间传递复杂的数据结构（如整个对象），但只用其中一部分 ⚠️ 一般
数据耦合 模块间仅通过参数传递基本数据或简单对象 ✅ 良好
非直接耦合 模块之间没有直接联系，通过消息队列或事件总线间接通信 🏆 最佳

面试重点：在 C#/.NET 中，我们通过依赖注入（DI）和面向接口编程将“控制耦合”或“内容耦合”转化为“数据耦合”或“非直接耦合”。

3. C# 代码对比示例

❌ 低内聚、高耦合（坏味道）

// 一个类既负责计算工资，又负责保存数据库，还负责发送邮件
public class EmployeeManager 
{
    public void ProcessPayroll(int employeeId) 
    {
        // 1. 计算逻辑（业务内聚）
        var salary = CalculateSalary(employeeId);
        
        // 2. 数据库操作（数据访问耦合）
        using (var conn = new SqlConnection("...")) 
        {
            conn.Execute("UPDATE Salaries SET Amount = @s WHERE Id = @id", new { s = salary, id = employeeId });
        }
        
        // 3. 邮件发送（外部服务耦合）
        var client = new SmtpClient();
        client.Send("hr@company.com", "employee@company.com", "Salary Slip", $"Your salary is {salary}");
    }
}

✅ 高内聚、低耦合（推荐）

// 1. 职责拆分：每个类只做一件事（高内聚）
public class SalaryCalculator 
{
    public decimal Calculate(int employeeId) { /* ... */ }
}

public interface IPayrollRepository 
{
    void UpdateSalary(int id, decimal amount); // 依赖抽象，低耦合
}

public interface IEmailSender 
{
    void SendSalarySlip(string email, decimal amount);
}

// 2. 通过构造函数注入依赖（解耦）
public class PayrollService 
{
    private readonly SalaryCalculator _calculator;
    private readonly IPayrollRepository _repo;
    private readonly IEmailSender _emailSender;

    public PayrollService(SalaryCalculator calculator, IPayrollRepository repo, IEmailSender emailSender) 
    {
        _calculator = calculator;
        _repo = repo;
        _emailSender = emailSender;
    }

    public void ProcessPayroll(int employeeId) 
    {
        var salary = _calculator.Calculate(employeeId);
        _repo.UpdateSalary(employeeId, salary);
        _emailSender.SendSalarySlip(GetEmail(employeeId), salary);
    }
}

4. 两者的辩证关系

  • 高内聚通常导致低耦合：当模块职责单一时，它对外部的需求就会减少，依赖自然变少。
  • 过度解耦的陷阱：为了追求极致的低耦合，可能会引入过多的中间层、接口和抽象，导致系统复杂度上升（过度设计）。需要在简洁性和灵活性之间取得平衡。

💡面试延伸追问（预判面试官后续提问）

  1. 如何判断一个类的内聚性是否过高或过低？

    • 考点：看类的方法是否操作同一组数据；看类名是否能用单一动词短语描述；看是否有“上帝类”（God Class）。

  2. 在微服务架构中，如何体现高内聚低耦合？

    • 考点：服务边界划分（DDD 限界上下文）、数据库私有化、异步通信（MQ）替代同步调用。

  3. 如果两个模块必须紧密协作，如何实现低耦合？

    • 考点：使用观察者模式（事件/委托）、中介者模式、或发布订阅机制，避免直接引用。

  4. 接口隔离原则（ISP）与内聚性有什么关系？

    • 考点：ISP 要求客户端不应依赖它不需要的接口，这实际上是在强制提高接口的内聚性，避免“胖接口”。

二、什么是策略设计模式

✅面试简答（考场口述答案）

策略模式是一种行为设计模式，它定义了一系列算法（策略），并将每个算法封装到独立的类中，使它们可以相互替换。客户端通过组合方式使用策略对象，而不是继承，从而在运行时动态切换算法。核心思想是"将算法的使用与算法的实现分离"。

📚深入解析

1. 核心组成

  • Strategy（策略接口）：定义所有支持算法的公共接口
  • ConcreteStrategy（具体策略）：实现不同的算法逻辑
  • Context（上下文）：持有一个策略对象的引用，委托策略执行具体算法

2. 关键特点

  • 开闭原则：新增策略只需添加新类，无需修改现有代码
  • 消除条件分支：避免大量 if-else 或 switch-case 判断
  • 运行时切换：可以在程序运行时动态更换算法
  • 组合优于继承：通过组合关系而非继承来实现多态

3. 适用场景

  • 同一接口有多种实现，需要根据不同条件选择
  • 算法需要频繁扩展或修改
  • 类中存在大量条件语句判断使用哪种算法

4. C# 中的典型应用

  • IComparer<T> 排序策略
  • ASP.NET Core 中的认证策略（IAuthorizationHandler）
  • 支付系统中的多种支付方式

💡参考实现（C#代码） 

// 1. 策略接口
public interface IPaymentStrategy
{
    void Pay(decimal amount);
}

// 2. 具体策略 - 支付宝支付
public class AlipayStrategy : IPaymentStrategy
{
    public void Pay(decimal amount)
    {
        Console.WriteLine($"使用支付宝支付: ¥{amount}");
    }
}

// 3. 具体策略 - 微信支付
public class WechatPayStrategy : IPaymentStrategy
{
    public void Pay(decimal amount)
    {
        Console.WriteLine($"使用微信支付: ¥{amount}");
    }
}

// 4. 具体策略 - 信用卡支付
public class CreditCardStrategy : IPaymentStrategy
{
    public void Pay(decimal amount)
    {
        Console.WriteLine($"使用信用卡支付: ¥{amount}");
    }
}

// 5. 上下文类
public class PaymentContext
{
    private IPaymentStrategy _strategy;

    // 构造函数注入策略
    public PaymentContext(IPaymentStrategy strategy)
    {
        _strategy = strategy;
    }

    // 运行时切换策略
    public void SetStrategy(IPaymentStrategy strategy)
    {
        _strategy = strategy;
    }

    // 执行支付
    public void ExecutePayment(decimal amount)
    {
        _strategy.Pay(amount);
    }
}

// 6. 使用示例
class Program
{
    static void Main()
    {
        var context = new PaymentContext(new AlipayStrategy());
        context.ExecutePayment(100m);  // 输出: 使用支付宝支付: ¥100

        // 运行时切换策略
        context.SetStrategy(new WechatPayStrategy());
        context.ExecutePayment(200m);  // 输出: 使用微信支付: ¥200
    }
}

💡面试延伸追问（预判面试官后续提问）

  1. 策略模式和工厂模式有什么区别？如何结合使用？

    • 策略关注算法替换，工厂关注对象创建；常结合使用，用工厂根据条件创建具体策略对象

  2. 策略模式和状态模式很相似，区别是什么？

    • 策略模式中各个策略独立无关联；状态模式中状态之间存在转换关系，且状态改变通常由内部触发

  3. 如果策略很多，每次都要手动创建和切换很麻烦，如何优化？

    • 可以结合工厂模式 + 字典/容器管理策略映射，或通过依赖注入框架自动注入

  4. 策略模式的缺点是什么？

    • 客户端必须了解不同策略的区别；策略类数量增多会增加系统复杂度

三、什么是依赖注入设计模式

✅面试简答（考场口述答案）

依赖注入（Dependency Injection, DI）是一种实现控制反转（IoC）的设计模式。其核心思想是将对象的创建和依赖关系的管理从类内部转移到外部容器。类不再自己 new 依赖对象，而是通过构造函数、属性或方法参数“接收”依赖。这样做实现了解耦，提高了代码的可测试性和可维护性。在 .NET 中，它通常通过内置的 IServiceCollection 容器来实现。

📚深入解析

1. 核心概念区分

  • 控制反转 (IoC)：一种设计思想，指将控制权从程序代码转移到框架或容器。
  • 依赖注入 (DI)：实现 IoC 的一种具体技术手段。
  • 依赖倒置原则 (DIP)：面向对象设计原则之一，高层模块不应依赖低层模块，二者都应依赖抽象。DI 是遵循 DIP 的最佳实践。

2. 三种注入方式

  • 构造函数注入（推荐）：最常用，保证对象创建时依赖已就绪，适合强制依赖。
  • 属性注入：适合可选依赖，但在 .NET Core 默认容器中支持较弱（需第三方库如 Autofac）。
  • 方法注入：较少见，通常在特定方法调用时才需要该依赖时使用。

3. .NET Core 中的生命周期管理（高频考点） ASP.NET Core 内置容器支持三种生命周期：

  • Transient（瞬时）：每次请求服务时都创建新实例。
  • Scoped（作用域）：在一次 HTTP 请求（或一个 Scope）内共享同一个实例。
  • Singleton（单例）：在整个应用程序生命周期内只创建一次实例。

4. 为什么需要 DI？

  • 解耦：业务逻辑不关心依赖的具体实现，只关心接口。
  • 可测试性：单元测试时可以轻松传入 Mock 对象替换真实依赖。
  • 可维护性：修改依赖实现无需修改调用方代码。

💡参考实现（C#代码） 

// 1. 定义抽象接口
public interface ILogger

💡面试延伸追问（预判面试官后续提问）

  1. 请详细解释 Transient、Scoped、Singleton 的区别及使用场景？

    • 陷阱：在 Singleton 中注入 Scoped 服务会导致“捕获依赖”问题（Scoped 变成事实上的 Singleton），可能引发内存泄漏或数据混乱。

  2. 什么是“捕获依赖”（Captive Dependency）？如何避免？

    • 当长生命周期的服务（如 Singleton）依赖于短生命周期的服务（如 Scoped/Transient）时发生。避免方法：不要在 Singleton 中直接注入 Scoped，或使用 IServiceScopeFactory 手动创建 Scope。

  3. 除了微软内置容器，你还用过哪些第三方 DI 容器？它们有什么优势？

    • 如 Autofac、DryIoc。优势通常包括：属性注入支持、更复杂的生命周期管理、程序集扫描自动注册、性能优化等。

  4. 如果构造函数中有多个参数，如何确定注入哪个实现？

    • 可以通过 [FromKeyedServices] (.NET 8+) 或第三方容器的命名/键值注册来解决；或者使用工厂模式包装依赖。

四、什么是模板方法设计模式

✅面试简答（考场口述答案）

模板方法模式是一种行为设计模式，它在父类中定义一个算法的骨架（流程），而将一些具体的步骤延迟到子类去实现。这样可以在不改变算法整体结构的前提下，让子类重新定义或扩展某些特定步骤。其核心原则是“流程固定，细节可变”，通常通过抽象类和虚方法/钩子方法来实现。

📚深入解析

1. 核心组成

  • AbstractClass（抽象类）：定义模板方法（通常是 final 或非虚的，防止被重写），以及若干抽象方法或虚方法作为待实现的步骤。
  • ConcreteClass（具体子类）：继承抽象类，实现或重写父类中的抽象/虚方法，提供具体业务逻辑。

2. 关键机制

  • 模板方法不可变：保证算法执行顺序和整体流程不被破坏。
  • 钩子方法（Hook）：在抽象类中提供默认空实现或基础实现的虚方法，子类可以选择性地覆盖，用于在流程的关键点插入自定义行为。
  • 好莱坞原则：“别调用我们，我们会调用你”。由父类控制流程并回调子类方法，而非子类主动调用父类。

3. 适用场景

  • 多个子类有相同的业务流程，仅部分步骤不同。
  • 需要固化一套标准处理流程，同时允许局部定制。
  • 重构时将重复代码提取到父类，消除代码冗余。

4. C# / .NET 中的典型应用

  • ASP.NET Core 中间件管道（IMiddleware 的 InvokeAsync 流程）。
  • EF Core 的数据库迁移生成器。
  • 单元测试框架（如 xUnit/NUnit 的 [SetUp]、[Test]、[TearDown] 生命周期）。
  • Stream 类的读写操作模板。

✍参考实现（C#代码） 

// 1. 抽象类：定义算法骨架
public abstract class DataProcessor
{
    // 模板方法：定义固定流程，禁止子类重写
    public void Process()
    {
        ReadData();
        ParseData();
        ValidateData();      // 钩子方法，可选覆盖
        SaveData();
        OnComplete();        // 钩子方法，通知完成
    }

    // 必须由子类实现的抽象步骤
    protected abstract void ReadData();
    protected abstract void ParseData();
    protected abstract void SaveData();

    // 钩子方法：提供默认实现，子类可选择性覆盖
    protected virtual void ValidateData()
    {
        Console.WriteLine("  [默认] 数据校验通过");
    }

    // 钩子方法：默认为空，子类按需实现
    protected virtual void OnComplete() { }
}

// 2. 具体子类A：CSV文件处理
public class CsvDataProcessor : DataProcessor
{
    protected override void ReadData()
        => Console.WriteLine("  读取CSV文件...");

    protected override void ParseData()
        => Console.WriteLine("  解析CSV格式...");

    protected override void SaveData()
        => Console.WriteLine("  保存到数据库...");

    // 覆盖了钩子方法，增加自定义校验
    protected override void ValidateData()

💡面试延伸追问（预判面试官后续提问）

  1. 模板方法模式和策略模式有什么区别？

    • 模板方法是继承关系，固定流程、变化步骤；策略模式是组合关系，整个算法可替换。模板方法强调“流程复用”，策略强调“算法互换”。

  2. 如果不想用继承，C# 中有没有替代方案实现类似效果？

    • 可以使用委托/Func<T> 参数传入步骤逻辑，或使用管道模式（Pipeline） + 中间件链，这在 .NET Core 中更为常见且灵活。

  3. 模板方法模式中，如何防止子类意外修改执行顺序？

    • 将模板方法声明为非虚方法（C# 中不加 virtual），或使用 sealed 关键字；在文档中明确标注该方法不应被重写。

  4. 这个模式有什么缺点？

    • 依赖继承，层次加深后难以维护；子类必须遵循父类契约，灵活性不如组合；每增加一种变体就需要新建子类，可能导致类爆炸。

  5. 为什么模板方法通常要标记为 sealed？

    • 防止子类意外重写整个流程导致算法骨架被破坏，确保只有预设的可变步骤能被定制。

  6. 模板方法的缺点是什么？如何缓解？

    • 缺点：继承耦合度高、子类数量膨胀、难以跨层级复用。缓解方案：结合策略模式将可变步骤抽取为独立策略对象注入，或用组合代替部分继承。

  7. 钩子方法和抽象方法有什么区别？

    • 抽象方法必须由子类实现；钩子方法有默认实现，子类可选择是否覆盖，用于控制流程中的可选分支。

  8. 在 ASP.NET Core 中哪些地方体现了模板方法模式？

    • BackgroundService.ExecuteAsync 定义了启动→运行→停止的骨架；中间件的 InvokeAsync 调用链也是固定流程+可插拔处理逻辑的体现。

五、什么是装饰器设计模式

✅面试简答（考场口述答案）

装饰器模式（Decorator Pattern）是一种结构型设计模式，它允许在不修改原有对象结构的情况下，动态地给对象添加新的功能。其核心思想是**“组合优于继承”**：通过创建一个包装类（Decorator），持有原对象的引用，并在调用原对象方法前后执行额外的逻辑。在 .NET 中，Stream 类族和 ASP.NET Core 的中间件管道是典型的装饰器模式应用。

📚深入解析

1. 核心组成

  • Component（组件接口）：定义原始对象和装饰器共同实现的接口。
  • ConcreteComponent（具体组件）：被装饰的原始对象，实现基本功能。
  • Decorator（抽象装饰器）：实现 Component 接口，并持有一个 Component 类型的引用（即被装饰对象）。
  • ConcreteDecorator（具体装饰器）：具体的功能增强类，在调用被装饰对象的方法前后添加额外行为。

2. 关键特点

  • 动态扩展：可以在运行时灵活组合多个装饰器，比静态继承更灵活。
  • 透明性：客户端面对的是统一的接口，无需关心对象是否被装饰。
  • 递归嵌套：装饰器可以层层包裹，形成“俄罗斯套娃”结构。
  • 避免类爆炸：如果使用继承来组合多种功能，会导致子类数量呈指数级增长（$2^n$），而装饰器只需 $n$ 个类。

3. 与代理模式（Proxy）的区别

  • 目的不同：装饰器旨在增强功能（如加日志、加密）；代理旨在控制访问（如权限校验、懒加载）。
  • 生命周期：装饰器通常由客户端主动创建并组合；代理通常由框架或容器管理，对客户端透明。

4. .NET 中的典型应用

  • System.IO.Stream：FileStream 是基础流，BufferedStream、GZipStream、CryptoStream 都是装饰器，可以层层包裹。
  • ASP.NET Core Middleware：每个中间件都可以看作是对 RequestDelegate 的装饰，形成处理管道。

{

    double GetCost();

💡面试延伸追问（预判面试官后续提问）

  1. 装饰器模式和继承有什么区别？为什么推荐用装饰器？

    • 继承是静态的、编译期确定的，且只能单继承；装饰器是动态的、运行期组合的，支持多重叠加。当功能组合多样时，继承会导致类爆炸，而装饰器保持类数量线性增长。

  2. 在 ASP.NET Core 中，中间件是如何体现装饰器模式的？

    • 每个中间件接收一个 RequestDelegate next，这其实就是下一个中间件（或被装饰的对象）。中间件在调用 next() 前后执行自己的逻辑，形成了链式装饰结构。

  3. 如果装饰器层级很深，性能会有影响吗？如何优化？

    • 会有轻微的性能开销（多次虚方法调用）。优化方案：避免不必要的深层嵌套；对于高频调用的场景，可以考虑将常用的装饰组合预先生成一个新的具体类（静态组合）。

  4. 装饰器模式如何解决“接口污染”问题？

    • 如果装饰器需要暴露原对象没有的新方法，就会破坏透明性。解决方案是：尽量只增强接口中已有的方法；如果必须新增功能，考虑使用适配器模式或重新设计接口。

六、什么是观察者设计模式

✅面试简答（考场口述答案）

观察者模式（Observer Pattern）是一种行为设计模式，定义了对象间的一种一对多的依赖关系。当一个对象（主题/Subject）的状态发生改变时，所有依赖于它的对象（观察者/Observer）都会得到通知并自动更新。核心思想是“解耦”：主题不需要知道观察者的具体实现，观察者也不需要知道主题的详细逻辑，二者通过接口或事件机制交互。在 C# 中，最典型的实现就是 event 和 delegate。

📚深入解析

1. 核心组成

  • Subject（主题/被观察者）：维护一个观察者列表，提供注册、移除和通知观察者的方法。
  • Observer（观察者）：定义一个更新接口，当收到主题通知时执行相应逻辑。
  • ConcreteSubject（具体主题）：存储状态，状态变化时触发通知。
  • ConcreteObserver（具体观察者）：实现更新逻辑，订阅具体主题。

2. 关键特点

  • 松耦合：主题和观察者之间仅通过抽象接口交互，互不依赖具体类。
  • 动态关联：可以在运行时随时添加或移除观察者。
  • 广播通信：主题向所有注册的观察者发送通知，支持一对多传播。

3. C# 中的原生支持

  • event 关键字：C# 语言级别对观察者模式的封装，基于委托（Delegate）。
  • IObservable<T> / IObserver<T>：.NET 4.0 引入的反应式编程接口，用于处理数据流。
  • 发布-订阅模式（Pub/Sub）：观察者模式的进阶版，通常引入消息代理（Broker）进一步解耦，如 RabbitMQ、Kafka。

4. 适用场景

  • 当一个对象的改变需要同时改变其他对象，且不知道具体有多少对象需要改变时。
  • 跨模块通信，如 UI 控件状态变化通知业务逻辑，或业务数据变化通知 UI 刷新。

💡参考实现（C#代码）

这里展示两种实现：一种是经典的接口实现，另一种是 C# 推荐的 event 实现。

方式一：经典接口实现（理解原理） 

// 1. 观察者接口
public interface IObserver
{
    void Update(string message);
}

// 2. 主题接口
public interface ISubject
{
    void Attach(IObserver observer);
    void Detach(IObserver observer);
    void Notify(string message);
}

// 3. 具体主题
public class NewsAgency : ISubject
{
    private readonly List<IObserver> _observers = new List<IObserver>();

    public void Attach(IObserver observer)
    {
        if (!_observers.Contains(observer))
            _observers.Add(observer);
    }

    public void Detach(IObserver observer)
    {
        _observers.Remove(observer);
    }

    public void Notify(string message)
    {
        foreach (var observer in _observers)
        {
            observer.Update(message);
        }
    }

    public void PublishNews(string news)
    {
        Console.WriteLine($"新闻社发布: {news}");
        Notify(news);
    }
}

// 4. 具体观察者
public class Subscriber : IObserver
{
    private readonly string _name;

    public Subscriber(string name)
    {
        _name = name;
    }

    public void Update(string message)
    {
        Console.WriteLine($"{_name} 收到通知: {message}");
    }
}

方式二：C# Event 实现（实战推荐） 

// 1. 定义事件参数
public class NewsEventArgs : EventArgs
{
    public string Message { get; }
    public NewsEventArgs(string message) => Message = message;
}

// 2. 主题（发布者）
public class NewsPublisher
{
    // 声明事件
    public event EventHandler<NewsEventArgs>? NewsPublished;

    public void Publish(string news)
    {
        Console.WriteLine($"发布新闻: {news}");
        // 触发事件
        NewsPublished?.Invoke(this, new NewsEventArgs(news));
    }
}

// 3. 观察者（订阅者）
public class NewsSubscriber
{
    private readonly string _name;

    public NewsSubscriber(string name)
    {
        _name = name;
    }

    // 订阅方法
    public void Subscribe(NewsPublisher publisher)
    {
        publisher.NewsPublished += OnNewsReceived;
    }

    // 取消订阅
    public void Unsubscribe(NewsPublisher publisher)
    {
        publisher.NewsPublished -= OnNewsReceived;
    }

    private void OnNewsReceived(object? sender, NewsEventArgs e)
    {
        Console.WriteLine($"{_name} 收到最新新闻: {e.Message}");
    }
}

class Program
{

    {
        var publisher = new NewsPublisher();
        var subscriber1 = new NewsSubscriber("用户A");
        var subscriber2 = new NewsSubscriber("用户B");

        // 订阅
        subscriber1.Subscribe(publisher);
        subscriber2.Subscribe(publisher);

        // 发布
        publisher.Publish("C# 12 正式发布！");
        
        // 输出:
        // 发布新闻: C# 12 正式发布！

        // 用户B 收到最新新闻: C# 12 正式发布！
    }
}

💡面试延伸追问（预判面试官后续提问）

  1. 观察者模式和发布-订阅模式有什么区别？

    • 观察者模式通常是同步的，主题直接调用观察者的方法，二者耦合度相对较高（主题知道观察者的接口）。
    • 发布-订阅模式通常引入中间件（Message Broker），发布者和订阅者完全解耦，且通常是异步的，适用于分布式系统。

  2. 在 C# 中使用 event 有什么优势？

    • event 基于委托，类型安全；
    • 封装性好：外部只能使用 += 和 -= 进行订阅/取消订阅，不能直接触发事件（只有类内部可以触发），防止了外部误操作。

  3. 如果观察者执行耗时操作，会阻塞主题吗？如何解决？

    • 是的，默认情况下是同步调用的，会阻塞。
    • 解决方案：在观察者内部使用异步逻辑（async/await），或者在主题中使用 Task.Run 并行触发通知（需注意异常处理和顺序问题）。

  4. 如何避免内存泄漏？

    • 如果观察者生命周期短于主题，且未取消订阅，主题持有的引用会导致观察者无法被 GC 回收。
    • 解决：务必在观察者销毁时调用 -= 取消订阅，或使用弱引用（WeakReference）管理观察者列表。

七、什么是控制反转

✅面试简答（考场口述答案）

控制反转（Inversion of Control，IoC）是一种设计原则，核心思想是将对象的创建、依赖关系的管理从代码内部转移到外部容器或框架中。传统方式是由调用者主动创建依赖对象（“正转”），而IoC则是将控制权交给容器，由容器负责注入依赖（“反转”）。最常见的实现方式是依赖注入（DI）。

📚深入解析

1. 什么是"控制"？什么是"反转"？

  • 控制：指对对象生命周期、依赖关系的管理权
  • 正转（传统方式）：类自己通过 new 关键字创建依赖对象 
    public class OrderService 
{
    private readonly PaymentGateway _gateway = new AlipayGateway(); // 硬编码依赖
}
  • 反转（IoC方式）：依赖对象由外部传入，类不再关心如何创建 
    public class OrderService 
{
    private readonly IPaymentGateway _gateway;

    public OrderService(IPaymentGateway gateway) // 依赖由外部注入
    {
        _gateway = gateway;
    }
}

2. IoC的核心价值

维度 传统方式 IoC方式
耦合度 高耦合，依赖具体实现 低耦合，依赖抽象接口
可测试性 难以Mock，单元测试困难 易于替换Mock，测试友好
可扩展性 修改依赖需改源码 只需更换注入的实现类
维护性 依赖关系分散在各处 依赖关系统一管理

3. IoC的常见实现方式

  1. 构造函数注入（最推荐）

    public class UserService 
{
    private readonly IUserRepository _repo;

    public UserService(IUserRepository repo) 
    {
        _repo = repo;
    }
}

  2. 属性注入

    public class UserService 
{
    [Inject]
    public IUserRepository Repository { get; set; }
}

  3. 方法注入（较少用）

    public void Initialize(IUserRepository repo) 
{
    _repo = repo;
}

4. ASP.NET Core中的IoC容器

ASP.NET Core内置了轻量级DI容器，在Program.cs中注册服务：

// 注册服务（三种生命周期）
builder.Services.AddScoped<IUserRepository, UserRepository>();  // 每次请求新建
builder.Services.AddSingleton<ICacheService, RedisCache>();    // 单例
builder.Services.AddTransient<IEmailSender, SmtpEmailSender>(); // 每次使用新建

// 自动注入到控制器
public class UserController : ControllerBase 
{
    private readonly IUserRepository _repo;
    
    public UserController(IUserRepository repo) // 框架自动注入
    {
        _repo = repo;
    }
}

5. IoC vs DI 的区别

  • IoC（控制反转）：是一种设计思想/原则
  • DI（依赖注入）：是实现IoC的具体技术手段
  • 类比：IoC是"把权力下放"的理念，DI是"通过构造函数传参"的具体做法

八、什么是组合优于继承原则

✅面试简答（考场口述答案）

组合优于继承（Composition over Inheritance）是面向对象设计的核心原则之一。它主张在复用代码时，优先使用组合（即在一个类中包含另一个类的实例）而不是继承（子类继承父类）。

因为继承会导致类之间产生强耦合和脆弱的基类问题，而组合通过依赖抽象接口，具有更高的灵活性、更低耦合度，更符合“开闭原则”，便于扩展和维护。

📚深入解析

1. 为什么继承有问题？（继承的痛点）

虽然继承能实现代码复用，但存在以下严重缺陷：

  • 破坏封装性：子类可以访问父类的 protected 成员，父类内部实现的改变可能意外破坏子类。
  • 脆弱基类问题（Fragile Base Class）：修改父类可能导致所有子类行为异常，牵一发而动全身。
  • 编译时耦合：继承关系在编译时就确定了，无法在运行时动态改变行为。
  • 层次结构爆炸：为了复用不同功能，可能导致类层级过深或出现菱形继承问题。
  • 单一职责违背：子类往往继承了父类所有方法，即使有些方法对子类无用。

2. 什么是组合？

组合是指一个类包含另一个类的对象作为其成员变量，通过调用该对象的方法来实现功能复用。

  • 关系描述：“Has-a”（有一个） vs “Is-a”（是一个）
  • 实现方式：通常结合接口或抽象类使用，依赖倒置。

3. 代码对比示例

❌ 继承方式（不推荐）

// 假设我们要实现一个带日志功能的数据库操作类
public class DatabaseLogger : Database 
{
    public override void Save() 
    {
        Console.WriteLine("开始保存...");
        base.Save(); // 强依赖父类实现
        Console.WriteLine("保存完成");
    }
}
// 问题：如果Database类修改了Save的内部逻辑，DatabaseLogger可能出错
// 问题：如果想换一种日志方式，必须新建子类

✅ 组合方式（推荐）

public interface ILogger 
{
    void Log(string message);
}

public class Database 
{
    private readonly ILogger _logger;
    
    // 通过构造函数注入日志组件（组合）
    public Database(ILogger logger) 
    {
        _logger = logger;
    }
    
    public void Save() 
    {
        _logger.Log("开始保存...");
        // 执行保存逻辑
        _logger.Log("保存完成");
    }
}

// 使用时可以灵活替换日志实现
var db = new Database(new FileLogger());
var db2 = new Database(new ConsoleLogger());

4. 组合的优势

维度 继承 组合
耦合度 高耦合（白盒复用） 低耦合（黑盒复用）
灵活性 编译时确定，僵化 运行时可替换，灵活
测试性 难以隔离测试父类 易于Mock依赖对象
扩展性 需修改类层级 只需新增组件类
职责清晰 容易混杂 各司其职

5. 什么时候可以用继承？

组合虽好，但继承并非完全无用，以下场景适合继承：

  • 真正的"is-a"关系：如 Dog is a Animal
  • 框架扩展点：如 ASP.NET Core 中继承 ControllerBase
  • 模板方法模式：父类定义算法骨架，子类实现具体步骤
  • 多态需求：需要统一接口处理不同类型对象

💡面试延伸追问（预判面试官后续提问）

  1. 组合和聚合有什么区别？

    • 考点：UML关系、生命周期绑定（组合是强拥有，聚合是弱拥有）

  2. 如何在C#中优雅地实现组合？是否一定要用接口？

    • 考点：依赖注入、策略模式、装饰器模式的应用

  3. 如果一个类需要复用多个类的功能，组合会不会导致类变得很臃肿？

    • 考点：外观模式（Facade）、中介者模式、合理拆分职责

  4. 请举例说明你在项目中如何用组合替代继承重构代码？

    • 考点：实际工程经验、重构能力

九、什么是模拟(Mocks)

✅面试简答（考场口述答案）

Mock（模拟对象） 是单元测试中的一种测试替身（Test Double），用于替代真实的依赖对象（如数据库、网络服务、文件系统）。

它的核心作用是：

  1. 隔离被测单元：确保测试只关注当前类的逻辑，不受外部环境影响。
  2. 控制行为：可以预设依赖对象的返回值或异常，覆盖各种边界情况。
  3. 验证交互：检查被测代码是否以预期的方式调用了依赖对象的方法（如调用次数、参数是否正确）。

在 .NET 生态中，最常用的 Mock 框架是 Moq。

📚深入解析

1. 为什么需要 Mock？

在真实开发中，许多依赖具有不确定性或副作用：

  • 数据库：数据状态不可控，写入操作有副作用。
  • 第三方 API：网络波动、速率限制、费用成本。
  • 时间/随机数：结果不可复现。

使用 Mock 可以将这些依赖替换为“听话”的假对象，使测试变得快速、稳定、可重复。

2. Mock vs Stub vs Fake 的区别

面试官常混淆这几个概念，需清晰区分：

类型 名称 核心目的 典型场景
Dummy 哑对象 仅为了凑齐参数，无实际逻辑 传入一个空的 ILogger
Stub 桩对象 提供预设数据（Return Value） 模拟数据库返回特定用户列表
Mock 模拟对象 验证交互行为（Verify Calls） 验证是否调用了 SendEmail()
Fake 假对象 拥有简化但真实的逻辑实现 内存中的 InMemoryDatabase

记忆口诀：Stub 管“返回什么”，Mock 管“怎么调用”。

3. C# 中 Moq 框架的核心用法

Moq 是基于动态代理实现的，要求被 Mock 的类型必须是接口或虚方法（virtual）。

基本流程：Create -> Setup -> Verify

using Moq;
using Xunit;

// 1. 定义接口
public interface IEmailService 
{
    void Send(string to, string subject);
}

public class OrderProcessor 
{
    private readonly IEmailService _emailService;

    public OrderProcessor(IEmailService emailService) 
    {
        _emailService = emailService;
    }

    public void ProcessOrder(string userEmail) 
    {
        // 业务逻辑...
        _emailService.Send(userEmail, "Order Confirmed");
    }
}

// 2. 编写单元测试
public class OrderProcessorTests 
{
    [Fact]
    public void ProcessOrder_ShouldSendEmail() 
    {
        // Arrange: 创建 Mock 对象
        var mockEmailService = new Mock<IEmailService>();
        
        // Setup: 预设行为（可选，如果是void方法通常不需要Setup返回值）
        // mockEmailService.Setup(x => x.Send(It.IsAny<string>(), It.IsAny<string>()))
        //     .Verifiable(); 

        var processor = new OrderProcessor(mockEmailService.Object);

        // Act: 执行被测方法
        processor.ProcessOrder("test@example.com");

        // Assert: 验证交互是否发生
        // 验证 Send 方法是否被调用了一次，且参数匹配
        mockEmailService.Verify(
            x => x.Send("test@example.com", "Order Confirmed"), 
            Times.Once
        );
    }
}

4. Mock 的关键特性

  • It.IsAny()：匹配任意类型的参数，用于忽略不关心的参数。
  • It.Is(predicate)：通过 Lambda 表达式精确匹配参数条件。
  • Times.Once / Times.Exactly(n)：验证调用次数。
  • Throws()：模拟依赖抛出异常，测试被测代码的容错能力。

5. 使用 Mock 的注意事项

  • 不要 Mock 值对象：如 string, int, DateTime，直接 new 即可。
  • 不要 Mock 你拥有的代码：如果依赖是你自己写的简单类，尽量用真实对象或 Fake，避免过度耦合测试实现细节。
  • Mock 只能针对接口或虚成员：C# 中密封类（sealed）或非虚方法无法被 Moq 直接 Mock（需借助 Microsoft.Fakes 或 JustMock 等重量级工具，但不推荐）。

💡面试延伸追问（预判面试官后续提问）

  1. Moq 是如何实现 Mock 接口的？原理是什么？

    • 考点：Castle DynamicProxy、运行时生成代理类、拦截方法调用。

  2. 如果我要测试的方法依赖的是一个具体类（非接口），且方法不是 virtual 的，怎么办？

    • 考点：重构代码提取接口（最佳实践）、使用 Wrapper 模式、或使用重型隔离框架（如 Typemock Isolator，但通常建议重构）。

  3. 什么是“过度 Mock”（Over-Mocking）？有什么危害？

    • 考点：测试与实现细节强耦合、重构困难、测试维护成本高。应优先测试行为而非内部协作细节。

  4. 在集成测试中还需要 Mock 吗？

    • 考点：集成测试通常使用真实依赖或容器化环境（如 Testcontainers），Mock 主要用于单元测试。

十、Debug版本和Release版本有什么区别

✅面试简答（考场口述答案）

Debug 和 Release 是 .NET 项目两种不同的构建配置，核心区别在于优化策略和调试信息。

  1. Debug 版：未开启代码优化，包含完整的 PDB 调试符号，定义了 DEBUG 常量。主要用于开发阶段，方便断点调试、查看变量，但运行速度较慢，体积较大。
  2. Release 版：开启了 JIT 和 AOT 代码优化（如内联、循环展开），通常不包含或仅包含精简的调试信息，定义了 RELEASE 常量。主要用于生产环境，运行速度快，体积小，但难以进行源码级调试。

📚深入解析

1. 核心差异对比表

特性 Debug 配置 Release 配置
代码优化 (Optimization) ❌ 关闭 (Disable) ✅ 开启 (Enable)
调试符号 (PDB) ✅ 完整生成 (Full) ⚠️ 可选/精简 (Portable/Pdb-only)
预处理器常量 DEBUG, TRACE TRACE (默认无 DEBUG)
JIT 编译器行为 禁用 JIT 优化，保留局部变量 启用 JIT 优化，可能移除未使用变量
性能 较慢 较快
文件大小 较大 较小
适用场景 本地开发、单元测试 生产部署、压力测试

2. 代码优化的具体表现（面试官喜欢问的细节）

在 Release 模式下，C# 编译器（Roslyn）和 JIT 编译器会执行以下优化：

  • 方法内联 (Inlining)：将短小的方法体直接嵌入调用处，减少方法调用开销。
  • 死代码消除 (Dead Code Elimination)：移除永远不会执行的代码或未使用的局部变量。
  • 寄存器分配优化：更积极地将变量放入 CPU 寄存器而非内存。
  • 循环优化：如循环展开（Loop Unrolling）。

⚠️ 坑点提示：由于优化，Release 模式下某些局部变量可能在调试时显示为“不可用”，或者代码执行顺序与源码不完全一致（重排序）。

3. 预处理器指令的影响

C# 支持条件编译，利用 #if DEBUG 可以区分不同环境的逻辑：

public void ProcessData() 
{
    #if DEBUG
    Console.WriteLine("进入调试模式，记录详细日志");
    // 开发时特有的检查逻辑
    System.Diagnostics.Debug.Assert(data != null);
    #endif

    // 无论 Debug 还是 Release 都会执行
    DoHeavyWork();
    
    #if RELEASE
    // 生产环境特有的逻辑，如性能监控上报
    Monitor.ReportPerformance();
    #endif
}

4. PDB (Program Database) 文件的作用

  • Debug 版：PDB 文件包含源码行号、局部变量名等完整信息，支持“编辑并继续”（Edit and Continue）。
  • Release 版：
    • 如果完全不带 PDB：发生异常时堆栈跟踪（Stack Trace）只显示方法名，没有行号。
    • 如果带 PDB（推荐生产环境做法）：可以定位到出错的行号，但无法查看局部变量的值，也不支持断点调试逻辑。

5. ASP.NET Core 中的体现

在 appsettings.json 中，通常通过环境变量 ASPNETCORE_ENVIRONMENT 来区分，但构建配置也会影响中间件的行为：

  • Debug: 启用开发者异常页面 (UseDeveloperExceptionPage)，显示详细错误堆栈。
  • Release: 启用全局异常处理中间件，返回通用错误页，隐藏敏感信息。

💡面试延伸追问（预判面试官后续提问）

  1. 为什么 Release 版本有时候比 Debug 版本难排查 Bug？

    • 考点：代码优化导致变量被优化掉、指令重排序、多线程竞争条件在高速运行下更容易暴露（Heisenbug）。

  2. 如何在生产环境（Release）中进行调试？

    • 考点：保留 PDB 文件、使用 Dump 文件分析（WinDbg/dotnet-dump）、远程调试（不推荐但可行）、增加结构化日志。

  3. TRACE 常量和 DEBUG 常量有什么区别？

    • 考点：TRACE 在 Debug 和 Release 中默认都定义，常用于生产环境的性能追踪或日志记录；DEBUG 仅在 Debug 模式下定义。

  4. JIT 优化会对异步代码（async/await）产生什么影响吗？

    • 考点：状态机生成的代码也会被优化，但 async 的状态转换逻辑复杂，过度优化可能导致堆栈跟踪断裂，理解状态机原理很重要。
