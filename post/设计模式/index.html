1、什么是单例设计模式

✅面试简答（考场口述答案）

单例模式保证一个类在整个应用程序生命周期中只有一个实例，并提供全局访问点。核心要点：私有构造函数、静态实例字段、线程安全的初始化方式。

📚深入解析

1. 核心特征

  • 唯一性：整个应用域中只存在一个实例
  • 全局访问：通过静态方法/属性获取实例
  • 延迟加载：通常在第一次使用时才创建（懒汉式）

2. C#常见实现方式

① 饿汉式（线程安全，简单）

public sealed class Singleton
{
    private static readonly Singleton _instance = new Singleton();
    
    private Singleton() { }
    
    public static Singleton Instance => _instance;
}

利用CLR类型初始化机制保证线程安全，但无法延迟加载

② 双重检查锁定（DCL，推荐）

public sealed class Singleton
{
    private static volatile Singleton _instance;
    private static readonly object _lock = new object();
    
    private Singleton() { }
    
    public static Singleton Instance
    {
        get
        {
            if (_instance == null)
            {
                lock (_lock)
                {
                    if (_instance == null)
                    {
                        _instance = new Singleton();
                    }
                }
            }
            return _instance;
        }
    }
}

volatile防止指令重排序，双重判断减少锁竞争

③ Lazy（.NET 4.0+ 最佳实践）

public sealed class Singleton
{
    private static readonly Lazy<Singleton> _lazyInstance 
        = new Lazy<Singleton>(() => new Singleton());
    
    private Singleton() { }
    
    public static Singleton Instance => _lazyInstance.Value;
}

线程安全、延迟加载、代码简洁，面试首选答案

④ 静态构造函数（保证线程安全）

public sealed class Singleton
{
    private static readonly Singleton _instance;
    
    static Singleton()
    {
        _instance = new Singleton();
    }
    
    private Singleton() { }
    
    public static Singleton Instance => _instance;
}

3. 关键注意事项

  • sealed修饰：防止子类化破坏单例
  • 私有构造函数：禁止外部直接new
  • 线程安全：多线程环境下必须保证只创建一个实例
  • 序列化问题：实现ISerializable或标记[Serializable]时需重写反序列化逻辑

💡面试延伸追问（预判面试官后续提问）

  1. Lazy底层是如何保证线程安全的？

    默认使用LazyThreadSafetyMode.ExecutionAndPublication，内部通过锁+双重检查实现

  2. 单例模式在ASP.NET Core中如何实现？与DI容器的Singleton生命周期有什么区别？

    DI容器中注册为AddSingleton<T>()，由容器管理生命周期；传统单例是手动管理

  3. 如果单例依赖其他服务，如何注入依赖？（考察对DI的理解）

    应放弃传统单例，改用DI容器管理的Singleton生命周期

  4. 单例模式的优缺点是什么？什么场景适合/不适合使用？

    优点：节省资源、全局访问；缺点：隐藏依赖、难以测试、违反单一职责

2、什么是建造者设计模式

✅面试简答（考场口述答案）

建造者模式（Builder Pattern）将复杂对象的构建过程与表示分离，使得同样的构建过程可以创建不同的表示。核心角色包括：产品类、抽象建造者、具体建造者、指挥者（Director）。适用于对象属性多、构造步骤复杂、需要不同组合的场景。

优点：封装性好，客户端无需知道内部构建细节；解耦构建过程与表示，易于扩展新的建造者；支持精细控制构建步骤；允许逐步构建对象，有助于将复杂的构建逻辑封装在单独的类中；特别是构造函数需要很多参数时，提高了可读性。

缺点：代码量增加，类数量变多；如果产品内部变化复杂，建造者也要同步修改，维护成本高；可能导致遗漏某些必需构建参数的风险，以及可能多次设置某个属性从而覆盖它的风险

📚深入解析

1. 核心思想

  • 分离构建与表示：客户端不直接操作复杂对象的内部结构
  • 逐步构建：通过链式调用或分步方法组装对象
  • 灵活组合：不同建造者可产生不同配置的对象

2. C#经典实现结构 

// 1. 产品类
public class Computer
{
    public string CPU { get; set; }
    public string RAM { get; set; }
    public string Storage { get; set; }
    public string GPU { get; set; }
    
    public override string ToString() 
        => $"CPU:{CPU}, RAM:{RAM}, Storage:{Storage}, GPU:{GPU}";
}

// 2. 抽象建造者
public abstract class ComputerBuilder
{
    protected Computer _computer = new Computer();
    
    public abstract void BuildCPU();
    public abstract void BuildRAM();
    public abstract void BuildStorage();
    public abstract void BuildGPU();
    
    public Computer GetResult() => _computer;
}

// 3. 具体建造者 - 游戏电脑
public class GamingComputerBuilder : ComputerBuilder
{
    public override void BuildCPU() => _computer.CPU = "Intel i9";
    public override void BuildRAM() => _computer.RAM = "32GB DDR5";
    public override void BuildStorage() => _computer.Storage = "1TB NVMe SSD";
    public override void BuildGPU() => _computer.GPU = "RTX 4090";
}

// 4. 具体建造者 - 办公电脑
public class OfficeComputerBuilder : ComputerBuilder
{
    public override void BuildCPU() => _computer.CPU = "Intel i5";
    public override void BuildRAM() => _computer.RAM = "16GB DDR4";
    public override void BuildStorage() => _computer.Storage = "512GB SSD";
    public override void BuildGPU() => _computer.GPU = "Integrated";
}

// 5. 指挥者
public class Director
{
    public Computer Construct(ComputerBuilder builder)
    {
        builder.BuildCPU();
        builder.BuildRAM();
        builder.BuildStorage();
        builder.BuildGPU();
        return builder.GetResult();
    }
}

// 使用示例
var director = new Director();
var gamingPC = director.Construct(new GamingComputerBuilder());
var officePC = director.Construct(new OfficeComputerBuilder());

3. C#现代简化版（链式调用 + Fluent API） 

public class ComputerBuilder
{
    private readonly Computer _computer = new Computer();
    
    public ComputerBuilder WithCPU(string cpu)
    {
        _computer.CPU = cpu;
        return this; // 返回自身支持链式调用
    }
    
    public ComputerBuilder WithRAM(string ram)
    {
        _computer.RAM = ram;
        return this;
    }
    
    public ComputerBuilder WithStorage(string storage)
    {
        _computer.Storage = storage;
        return this;
    }
    
    public ComputerBuilder WithGPU(string gpu)
    {
        _computer.GPU = gpu;
        return this;
    }
    
    public Computer Build() => _computer;
}

// 使用更简洁
var pc = new ComputerBuilder()
    .WithCPU("Intel i7")
    .WithRAM("16GB")
    .WithStorage("512GB SSD")
    .Build();

4. 与工厂模式的区别

维度 工厂模式 建造者模式
关注点 创建什么对象 如何一步步构建对象
复杂度 简单对象 复杂对象，多步骤
返回结果 直接返回完整对象 分步组装后返回
灵活性 选择不同类型 同一类型不同配置

💡面试延伸追问（预判面试官后续提问）

  1. 建造者模式和工厂模式有什么区别？什么时候用哪个？

    工厂关注"创建哪种类型"，建造者关注"如何组装复杂对象"。对象结构简单用工厂，步骤多/配置多用建造者

  2. C#中StringBuilder是不是建造者模式的典型应用？

    是的，StringBuilder通过Append逐步构建字符串，最后ToString()获取结果，是标准建造者模式

  3. ASP.NET Core中哪里用到了建造者模式？

    WebHost.CreateDefaultBuilder()、ConfigurationBuilder、HttpClientBuilder都使用了Fluent API风格的建造者模式

  4. 如果建造过程中某一步失败如何处理？（考察健壮性设计）

    可在Build()方法中校验必填项，抛出异常；或使用TryBuild()返回bool+out参数

3、什么是适配器设计模式

✅面试简答（考场口述答案）

适配器模式（Adapter Pattern）是一种结构型设计模式，它的作用是将一个类的接口转换成客户希望的另一个接口。核心目的是解决接口不兼容的问题，让原本因接口不匹配而无法一起工作的类能够协同工作。就像生活中的电源转换插头。

📚深入解析

1. 核心角色

  • 目标接口（Target）：客户端所期望的接口标准。
  • 适配者（Adaptee）：需要被适配的现有类，其接口与目标不兼容。
  • 适配器（Adapter）：实现目标接口，并内部持有适配者的引用，将请求转发给适配者处理。

2. C# 两种实现方式

① 对象适配器（组合，推荐）

通过组合方式持有 Adaptee 实例，符合“组合优于继承”原则，更灵活。

// 1. 目标接口：客户端期望的标准
public interface ITarget
{
    string GetRequest();
}

// 2. 适配者：现有的、接口不兼容的类
public class Adaptee
{
    public string GetSpecificRequest()
    {
        return "Adaptee specific request";
    }
}

// 3. 适配器：实现目标接口，内部调用适配者
public class Adapter : ITarget
{
    private readonly Adaptee _adaptee;

    public Adapter(Adaptee adaptee)
    {
        _adaptee = adaptee;
    }

    public string GetRequest()
    {
        // 关键：在这里进行接口转换/逻辑适配
        return $"Adapter: {_adaptee.GetSpecificRequest()}";
    }
}

// 使用
var adaptee = new Adaptee();
ITarget target = new Adapter(adaptee);
Console.WriteLine(target.GetRequest());

② 类适配器（多重继承，C#不支持）

C# 不支持多重继承，因此无法像 C++ 那样通过继承 Adaptee 和 Target 来实现类适配器。在 C# 中通常只使用对象适配器。

3. 常见应用场景

  • 旧系统迁移：新代码调用旧系统的 API，但旧 API 参数或返回格式不符合新规范。
  • 第三方库集成：引入的第三方 SDK 接口定义与自家系统标准不一致。
  • 数据格式转换：例如将 XML 数据源适配为 JSON 接口供前端使用。

4. .NET 中的典型应用

  • ASP.NET Core 中间件：某些中间件本质上是将 HTTP 请求适配为特定的处理管道。
  • LINQ to Entities / EF Core：将 LINQ 表达式树适配为 SQL 查询语句。
  • IDataAdapter：在 ADO.NET 中，SqlDataAdapter 等实现了 IDbDataAdapter，用于填充 DataSet，屏蔽了底层数据库驱动的差异。

💡面试延伸追问（预判面试官后续提问）

  1. 适配器模式和代理模式（Proxy）有什么区别？

    目的不同：适配器是为了改变接口以匹配客户端；代理是为了控制访问（如权限、缓存、日志），接口通常保持不变。 关系不同：适配器连接两个无关的类；代理通常与被代理类实现同一接口。

  2. 适配器模式和装饰器模式（Decorator）有什么区别？

    侧重点不同：适配器侧重接口转换，不增加新功能；装饰器侧重动态添加行为，接口保持不变。 结构不同：适配器内部持有的是“异类”（Adaptee）；装饰器内部持有的是“同类”（Component）。

  3. 在微服务架构中，适配器模式有什么体现？

    防腐层（Anti-Corruption Layer, ACL）：在领域驱动设计（DDD）中，ACL 常使用适配器模式，将外部服务的杂乱数据模型适配为内部整洁的领域模型，保护核心领域不受外部污染。

  4. 如果适配过程非常复杂，是否应该直接在 Adapter 中写大量逻辑？

    不建议。如果适配逻辑复杂，应遵循单一职责原则，将复杂的转换逻辑提取到独立的转换器（Converter/Mapper）类中，Adapter 仅负责协调调用。

4、什么是桥接设计模式

✅面试简答（考场口述答案）

桥接模式（Bridge Pattern）是一种结构型设计模式，它将抽象部分与实现部分分离，使它们可以独立地变化。核心思想是“组合优于继承”，通过持有接口引用来代替多层继承，解决因多维度变化导致的类爆炸问题。

📚深入解析

1. 核心痛点：为什么需要桥接？

假设我们要开发一个绘图系统：

  • 形状维度：圆形、矩形
  • 颜色维度：红色、蓝色

如果使用继承，我们需要创建：RedCircle, BlueCircle, RedRectangle, BlueRectangle。 如果有 $M$ 种形状和 $N$ 种颜色，就需要 $M \times N$ 个类。增加一种颜色或形状，类数量呈指数级增长（类爆炸）。

桥接模式将“形状”和“颜色”拆分开，通过组合连接，只需 $M + N$ 个类。

2. C# 代码实现 

// 1. 实现部分接口（Implementor）：定义颜色的行为
public interface IColor
{
    string ApplyColor();
}

// 具体实现：红色
public class RedColor : IColor
{
    public string ApplyColor() => "Red";
}

// 具体实现：蓝色
public class BlueColor : IColor
{
    public string ApplyColor() => "Blue";
}

// 2. 抽象部分（Abstraction）：定义形状的行为，并持有颜色引用
public abstract class Shape
{
    protected IColor _color; // 桥接的关键：组合而非继承

    protected Shape(IColor color)
    {
        _color = color;
    }

    public abstract void Draw();
}

// 3. 扩展抽象：圆形
public class Circle : Shape
{
    public Circle(IColor color) : base(color) { }

    public override void Draw()
    {
        Console.WriteLine($"Drawing a {_color.ApplyColor()} Circle");
    }
}

// 4. 扩展抽象：矩形
public class Rectangle : Shape
{
    public Rectangle(IColor color) : base(color) { }

    public override void Draw()
    {
        Console.WriteLine($"Drawing a {_color.ApplyColor()} Rectangle");
    }
}

// 使用示例
IColor red = new RedColor();
Shape circle = new Circle(red);
circle.Draw(); // Output: Drawing a Red Circle

IColor blue = new BlueColor();
Shape rect = new Rectangle(blue);
rect.Draw();   // Output: Drawing a Blue Rectangle

3. 关键要点

  • 分离维度：识别出对象中两个独立变化的维度（如：形状 vs 颜色，平台 vs 业务逻辑）。
  • 组合替代继承：抽象类中持有一个实现接口的引用。
  • 动态切换：可以在运行时动态更换实现（例如把圆形的颜色从红换成蓝，只需替换 _color 引用）。

4. .NET 中的典型应用

  • ADO.NET：DbConnection（抽象）与具体的驱动实现（如 SqlConnection, MySqlConnection）之间体现了桥接思想，允许上层代码不依赖具体数据库驱动。
  • ASP.NET Core Logging：ILogger（抽象）与各种 ILoggerProvider（如 Console, Debug, File）分离，可以动态添加不同的日志输出目标。

💡面试延伸追问（预判面试官后续提问）

  1. 桥接模式和适配器模式有什么区别？

    意图不同：桥接是为了解耦，让两个维度独立扩展；适配器是为了兼容，让不匹配的接口能一起工作。 时间点不同：桥接通常在系统设计初期就规划好；适配器通常用于后期集成旧系统或第三方库。

  2. 桥接模式和策略模式（Strategy）很像，怎么区分？

    结构相似：都是组合接口。 侧重点不同：

    • 策略模式关注的是算法/行为的替换（如排序算法、支付策略），通常只有一个维度变化。
    • 桥接模式关注的是结构化的解耦，通常涉及两个维度的正交变化（如：UI控件 vs 操作系统平台）。

  3. 什么场景下不适合用桥接模式？

    如果对象只有一个变化维度，或者变化非常稳定，直接使用继承更简单直观。桥接模式会增加系统的复杂度（类增多、关系变复杂），只有在确实存在多维变化且需要独立扩展时才使用。

  4. 在微服务或分布式系统中，桥接模式有什么体现？

    **SPI（Service Provider Interface）**机制：Java 和 .NET 中都广泛使用 SPI，定义标准接口（Abstraction），由不同的厂商提供具体实现（Implementor），通过配置文件或 DI 容器进行桥接。

5、什么是工厂方法设计模式

✅面试简答（考场口述答案）

工厂方法模式（Factory Method Pattern）定义了一个创建对象的接口，但由子类决定实例化哪一个类。它将对象的创建延迟到子类中。核心特征是：父类定义抽象工厂方法，具体子类实现该方法来创建具体产品。它解决了简单工厂模式违反“开闭原则”的问题。

📚深入解析

1. 核心角色

  • 抽象产品（Product）：定义产品的接口。
  • 具体产品（Concrete Product）：实现产品接口的具体类。
  • 抽象创建者（Creator）：声明工厂方法，返回抽象产品类型。
  • 具体创建者（Concrete Creator）：重写工厂方法，返回具体的产品实例。

2. C# 代码实现 

// 1. 抽象产品
public interface IButton
{
    void Render();
}

// 2. 具体产品
public class WindowsButton : IButton
{
    public void Render() => Console.WriteLine("Render Windows Button");
}

public class MacButton : IButton
{
    public void Render() => Console.WriteLine("Render Mac Button");
}

// 3. 抽象创建者
public abstract class Dialog
{
    // 工厂方法：由子类决定创建什么按钮
    public abstract IButton CreateButton();

    public void RenderDialog()
    {
        // 业务逻辑中使用产品
        IButton btn = CreateButton();
        btn.Render();
    }
}

// 4. 具体创建者
public class WindowsDialog : Dialog
{
    public override IButton CreateButton() => new WindowsButton();
}

public class MacDialog : Dialog
{
    public override IButton CreateButton() => new MacButton();
}

// 使用示例
Dialog dialog = new WindowsDialog();
dialog.RenderDialog(); // Output: Render Windows Button

3. 与简单工厂模式的区别

维度 简单工厂 (Simple Factory) 工厂方法 (Factory Method)
结构 一个静态方法包含所有 if/else 多个子类，每个子类负责一种产品
扩展性 新增产品需修改工厂类（违反开闭原则） 新增产品只需新增子类（符合开闭原则）
复杂度 低，适合产品少且固定 高，适合产品族复杂且经常扩展

4. .NET 中的典型应用

  • ASP.NET Core Middleware：IMiddlewareFactory 接口允许自定义中间件的创建逻辑。
  • Entity Framework Core：IDbContextFactory<T> 用于在特定场景（如 Blazor Server）下创建 DbContext 实例。
  • System.Collections.Immutable：许多不可变集合的创建通过工厂方法暴露，隐藏内部复杂的构建逻辑。

💡面试延伸追问（预判面试官后续提问）

  1. 工厂方法模式和抽象工厂模式有什么区别？

    工厂方法针对单一产品等级结构（如只创建 Button）；抽象工厂针对一族相关产品（如同时创建 Button、Checkbox、Textbox）。抽象工厂通常由多个工厂方法组成。

  2. 为什么工厂方法模式符合开闭原则？

    因为当需要新增一种产品时，不需要修改现有的工厂类或客户端代码，只需要新增一个具体创建者子类即可。

  3. 在依赖注入（DI）容器中，还需要手写工厂方法吗？

    大多数情况下不需要，DI 容器（如 ASP.NET Core 内置容器）本身就是一个超级工厂。但如果创建对象需要复杂的运行时参数或条件判断，手写工厂方法并将其注册为服务会更清晰。

  4. 工厂方法模式的缺点是什么？

    类的数量会成倍增加（每增加一个产品就要增加一个具体创建者类），增加了系统的复杂性。如果产品层级很简单，使用简单工厂或直接 new 可能更合适。
