一、等值运算符(==) 和 Equals方法有什么区别

✅面试简答（考场口述答案）

== 和 Equals() 的核心区别在于比较的机制和多态性：

  1. == (运算符)：
    • 默认情况下，对于引用类型比较的是内存地址（引用是否相同）；对于值类型比较的是内容（逐位比较）。
    • 它是静态绑定的，编译时根据变量的声明类型决定调用哪个重载，不具备运行时多态性。
  2. Equals() (方法)：
    • 是 System.Object 的虚方法，默认行为与 == 类似（引用类型比地址，值类型比内容）。
    • 它是动态绑定的，支持运行时多态。子类可以重写 Equals 来定义“逻辑相等”（即内容相同即为相等，即使不是同一个对象）。
  3. 特例：string 类型重写了 == 和 Equals，因此两者都用于比较字符串的内容。

📚深入解析

1. 行为对比表

特性 == 运算符 Equals() 方法
绑定方式 静态绑定 (编译时确定) 动态绑定 (运行时确定，虚方法)
引用类型默认 比较引用地址 (Reference Equality) 比较引用地址 (除非被重写)
值类型默认 比较内容 (Value Equality) 比较内容 (通过反射或逐位比较)
可重载/重写 可以重载 (operator ==) 可以重写 (override)
Null 处理 null == null 返回 true obj.Equals(null) 抛出异常 (需先判空)
String 类型 比较内容 比较内容

2. 引用类型的陷阱：静态绑定 vs 动态绑定

这是面试官最喜欢考的代码题。

class Person
{
    public string Name { get; set; }
}

// 假设我们重写了 Equals 但没有重载 ==
public override bool Equals(object obj)
{
    if (obj is Person other) return this.Name == other.Name;
    return false;
}

// 测试
Person p1 = new Person { Name = "Alice" };
Person p2 = new Person { Name = "Alice" };
object o1 = p1;
object o2 = p2;

Console.WriteLine(p1 == p2);       // False: 编译时类型是 Person，调用默认的引用比较
Console.WriteLine(p1.Equals(p2));  // True: 运行时多态，调用重写的 Equals

Console.WriteLine(o1 == o2);       // False: 编译时类型是 object，调用 object 的 == (比地址)
Console.WriteLine(o1.Equals(o2));  // True: 运行时多态，调用 Person 重写的 Equals
  • 结论：== 看的是“声明类型”，Equals 看的是“实际类型”。

3. 值类型的特殊性

  • ==：对于结构体（struct），如果未重载 ==，编译器会报错（C# 7.0 之前）或使用默认的值比较。通常建议为 struct 重载 == 以提高性能（避免反射）。
  • Equals：ValueType 基类实现了 Equals，它使用反射来比较所有字段。如果结构体很大，性能较差。最佳实践是为 struct 实现 IEquatable<T> 接口并重写 Equals。

4. String 的特殊性

string 是引用类型，但微软为其重载了 == 并重写了 Equals，使它们都比较字符序列的内容。

  • string a = "hello"; string b = "hello";
  • a == b 为 True。
  • a.Equals(b) 为 True。
  • 注意：如果是两个不同的 object 引用指向相同的字符串内容，== 依然比较内容（因为编译器会根据操作数类型解析到 string 的重载版本，但如果强制转为 object 再比 == 则比地址）。

5. 最佳实践：如何正确实现相等性？

如果你自定义了一个类，希望基于内容判断相等，必须同时做三件事：

  1. 重写 Equals(object obj)。
  2. 重载 operator == 和 operator !=。
  3. 重写 GetHashCode()。（非常重要！否则在 Dictionary/HashSet 中会出错）
public class Product : IEquatable<Product>
{
    public int Id { get; set; }

    public bool Equals(Product other)
    {
        if (other is null) return false;
        return Id == other.Id;
    }

    public override bool Equals(object obj)
    {
        return Equals(obj as Product);
    }

    public override int GetHashCode()
    {
        return Id.GetHashCode();
    }

    public static bool operator ==(Product left, Product right)
    {
        if (left is null) return right is null;
        return left.Equals(right);
    }

    public static bool operator !=(Product left, Product right)
    {
        return !(left == right);
    }
}

💡面试延伸追问（预判面试官后续提问）

  1. 为什么重写 Equals 时必须重写 GetHashCode？
    • 考点：哈希集合（如 Dictionary, HashSet）首先通过 GetHashCode 确定桶的位置，再通过 Equals 确认具体元素。如果两个对象 Equals 为 true 但 HashCode 不同，它们会被放在不同的桶里，导致集合中出现重复元素或查找失败。
  2. ReferenceEquals 是什么？它和 == 有什么区别？
    • 考点：Object.ReferenceEquals(a, b) 始终比较内存地址，即使 a 和 b 是字符串或重载了 == 的类型。它是判断“是否是同一个对象实例”的最可靠方法。
  3. IEquatable<T> 接口的作用是什么？为什么推荐实现它？
    • 考点：IEquatable<T>.Equals(T other) 是强类型的，避免了装箱（Boxing）和类型检查开销。泛型集合（如 List<T>.Contains）会优先调用这个接口的方法，性能比 object.Equals 更高。
  4. 在 EF Core 或 LINQ to SQL 中，== 是如何工作的？
    • 考点：在表达式树中，== 会被翻译成 SQL 的 = 语句。此时它不执行 C# 的比较逻辑，而是由数据库引擎执行比较。

二、深拷贝和浅拷贝的区别是什么

✅面试简答（考场口述答案）

浅拷贝（Shallow Copy）和深拷贝（Deep Copy）的核心区别在于对引用类型成员的处理方式：

  1. 浅拷贝：只复制对象本身。如果对象中包含引用类型的字段，它只复制引用地址，而不复制引用的实际对象。结果是：原对象和副本指向堆内存中的同一个子对象，修改其中一个会影响另一个。
  2. 深拷贝：不仅复制对象本身，还会递归地复制所有引用的子对象。结果是：原对象和副本在内存中是完全独立的，互不影响。

一句话总结：浅拷贝是“复印件”，深拷贝是“重新打印一份”。

📚深入解析

1. 内存模型图解

假设有一个类 Person，里面包含一个 Address 对象。

  • 浅拷贝后：
    • Person1 和 Person2 是两个不同的 Person 实例。
    • 但 Person1.Address 和 Person2.Address 指向同一个 Address 实例。
  • 深拷贝后：
    • Person1 和 Person2 是两个不同的 Person 实例。
    • Person1.Address 和 Person2.Address 也指向两个不同的 Address 实例。

2. C# 中的实现方式

A. 浅拷贝的实现

C# 提供了内置支持：

  1. Object.MemberwiseClone()：这是最基础的浅拷贝方法，它会创建一个新对象，并将非静态字段从当前对象复制到新对象。对于值类型，执行逐位复制；对于引用类型，只复制引用。
  2. 赋值运算符：对于结构体（Struct），默认赋值就是浅拷贝（但因为结构体通常不含复杂引用，表现像深拷贝，除非含有类字段）。
public class Person : ICloneable
{
    public string Name { get; set; }
    public Address Address { get; set; } // 引用类型

    // 浅拷贝
    public object Clone()
    {
        return this.MemberwiseClone(); 
    }
}
B. 深拷贝的实现

C# 没有内置的“一键深拷贝”方法，常见方案有：

  1. 手动实现：在构造函数或 Clone 方法中，手动 new 每一个子对象并复制属性。最安全但代码量大。
  2. 序列化/反序列化：将对象序列化为 JSON 或 Binary，再反序列化回来。
    • 优点：简单，一行代码搞定。
    • 缺点：性能较差，且要求对象可序列化。
  3. 反射/表达式树：编写通用工具类，通过反射递归复制所有属性。
  4. 第三方库：如 AutoMapper (配置 CreateMap<Person, Person>().ForMember(...)), Newtonsoft.Json。
// 使用 JSON 进行简单的深拷贝示例
public T DeepClone<T>(T obj)
{
    var json = JsonConvert.SerializeObject(obj);
    return JsonConvert.DeserializeObject<T>(json);
}

3. 关键陷阱与注意事项

  • 字符串的特殊性：string 是引用类型，但具有不可变性。所以在浅拷贝中，即使两个对象共享同一个 string 引用，修改其中一个对象的 string 属性（实际上是创建了新字符串并改变引用）不会影响另一个。因此，对于只包含基本类型和 string 的对象，浅拷贝往往足够使用。
  • 循环引用：如果使用递归反射或简单的序列化进行深拷贝，遇到对象 A 引用 B，B 又引用 A 的情况，可能会导致栈溢出或无限循环。成熟的序列化库（如 Newtonsoft）通常能处理这种情况。
  • 性能开销：深拷贝涉及大量内存分配和 CPU 计算。在高性能场景（如游戏开发、高频交易）中，应尽量避免频繁深拷贝，转而使用不可变对象（Immutable Objects）或结构体（Structs）。

💡面试延伸追问（预判面试官后续提问）

  1. MemberwiseClone 是深拷贝还是浅拷贝？它能拷贝私有字段吗？
    • 考点：它是浅拷贝。它能拷贝私有字段，因为它是 Object 类的受保护方法，直接操作内存布局。
  2. 为什么结构体（Struct）通常不需要担心深拷贝问题？
    • 考点：结构体是值类型，赋值时直接拷贝数据。但如果结构体内部包含引用类型字段（如 class 或 array），这些引用依然会被浅拷贝。所以严格来说，含引用字段的 struct 赋值也是浅拷贝。
  3. 在什么场景下必须使用深拷贝？
    • 考点：当需要备份对象状态以便后续回滚（如撤销操作）、多线程间传递可变对象以防止竞争条件、或者需要将对象发送到远程服务而隔离本地状态时。
  4. 什么是“写时复制”（Copy-on-Write）？它如何优化拷贝性能？
    • 考点：这是一种优化策略。在拷贝时先不真正复制数据，而是共享同一块内存。只有当某个副本试图修改数据时，才真正执行复制操作。.NET 中的 ImmutableArray 或某些数据库引擎使用了类似思想。

三、什么是垃圾回收器(Garbage Collector, GC)

✅面试简答（考场口述答案）

垃圾回收器（GC） 是 .NET 运行时（CLR/CoreCLR）中负责自动内存管理的核心组件。

  • 核心职责：自动分配托管堆内存，识别并回收不再被使用的对象，防止内存泄漏。
  • 工作原理：基于可达性分析算法（从 GC Roots 出发遍历引用链），而非引用计数。采用分代假设（Generational Hypothesis），将对象分为 Gen 0、Gen 1、Gen 2 三代，新生代频繁回收，老年代偶尔回收，以平衡性能与吞吐量。
  • 触发时机：当某一代内存耗尽、系统内存不足或手动调用 GC.Collect() 时触发。

📚深入解析

1. 为什么需要 GC？

手动管理内存（如 C/C++）容易导致两类严重问题：

  • 内存泄漏：忘记释放内存，导致程序越跑越慢直至崩溃。
  • 悬空指针：释放了仍在使用的内存，导致不可预测的崩溃。 GC 通过自动化解决了这两个问题，让开发者专注于业务逻辑。

2. 核心算法：可达性分析 (Reachability Analysis)

GC 不依赖“引用计数”（因为无法处理循环引用）。它从一组称为 GC Roots 的根对象开始遍历：

  • GC Roots 包括：
    • 当前所有线程栈上的局部变量和参数。
    • 静态字段（Static Fields）。
    • JIT 编译器缓存中的临时变量。
    • 终结器队列（Finalizer Queue）中的对象。
  • 判定：能从 GC Roots 到达的对象是“存活”的；无法到达的对象即为“垃圾”，可被回收。

3. 分代模型 (Generational Model)

基于两个经验假设：

  1. 大多数对象朝生夕死（90%+ 的对象在第一次 GC 时就被回收）。
  2. 活得越久的对象，未来存活的概率越大。
代 描述 回收频率 典型对象
Gen 0 新分配的对象 极高 临时变量、短生命周期对象
Gen 1 Gen 0 回收后幸存的对象 中等 缓冲区、短期缓存
Gen 2 Gen 1 回收后幸存的对象 极低 单例、静态数据、长连接
  • 晋升机制：对象每经历一次 GC 且未被回收，就晋升一代。Gen 2 是最高代，再回收仍存活则留在 Gen 2。

4. GC 模式

  • 工作站 GC (Workstation)：默认模式，为客户端应用优化，低延迟，并发回收。
  • 服务器 GC (Server)：为高吞吐服务端应用优化（ASP.NET Core 默认启用），每个 CPU 核心有独立的堆和 GC 线程，暂停时间可能较长但总吞吐量更高。

5. 大对象堆 (LOH)

大于 85,000 字节 的对象直接分配到 LOH（属于 Gen 2）。LOH 默认不压缩（避免移动大对象的开销），容易产生碎片。.NET Core 3.0+ 支持按需压缩 LOH。

💡面试延伸追问（预判面试官后续提问）

  1. 什么是 GC Roots？为什么静态变量会导致内存泄漏？
    • 考点：静态变量本身就是 GC Root，只要 AppDomain 未卸载，它们引用的对象永远不会被回收。如果静态集合不断 Add 而不清理，就会导致内存持续增长。
  2. GC.Collect() 应该手动调用吗？为什么？
    • 考点：绝大多数情况下不应该。GC 的自适应算法比人工判断更精准。手动强制 Full GC 会导致长时间 STW（Stop-The-World），破坏分代假设，反而降低性能。仅在明确知道有大量内存刚释放且后续有高负载操作前才考虑使用。
  3. 什么是 Finalizer（终结器/析构函数）？它对 GC 有什么影响？
    • 考点：带 ~ClassName() 的对象在第一次 GC 时不会被立即回收，而是放入终结器队列等待执行。这会导致对象至少多存活一代（Promotion），增加 GC 压力。应优先使用 IDisposable + using 模式。
  4. 弱引用（WeakReference）是什么？它和 GC 有什么关系？
    • 考点：弱引用允许对象被 GC 回收，同时保留访问能力。适用于缓存场景：内存充足时保留缓存，内存紧张时 GC 可自动回收缓存对象而不阻止回收。

四、什么是可空类型

✅面试简答（考场口述答案）

**可空类型（Nullable Types）**允许值类型（如 int, bool, DateTime）拥有 null 值。

  • 本质：它是 System.Nullable<T> 结构体的语法糖，其中 T 必须是非空的值类型。
  • 语法：int? 等价于 Nullable<int>。
  • 核心属性：
    • HasValue：判断是否包含有效值。
    • Value：获取实际值（如果 HasValue 为 false 则抛出异常）。
  • 用途：主要用于数据库映射（数据库中字段可为 NULL）、API 交互或表示“未初始化/未知”的状态。
  • 扩展：C# 8.0 引入了可空引用类型（Nullable Reference Types），通过静态分析在编译期提醒开发者检查引用类型的 null 情况，但这只是编译器特性，运行时行为不变。

📚深入解析

1. 底层实现原理

int? 并不是一个特殊的魔法类型，它在编译后就是 Nullable<int>。 Nullable<T> 是一个轻量级的泛型结构体（Struct），内部包含两个字段：

  1. T value：存储实际的值。
  2. bool hasValue：标记是否有值。
// 伪代码展示 Nullable<T> 的结构
public struct Nullable<T> where T : struct
{
    private bool hasValue;
    internal T value;

    public bool HasValue => hasValue;
    public T Value 
    { 
        get 
        {
            if (!hasValue) ThrowHelper.ThrowInvalidOperationException();
            return value;
        } 
    }
    
    // 隐式转换：T -> Nullable<T>
    public static implicit operator Nullable<T>(T value) => new Nullable<T>(value, true);
}

2. 常用操作与语法糖

  • 赋值： 
    int? a = 10; // 有值
int? b = null; // 无值
  • 取值： 
    if (a.HasValue) 
{
    int val = a.Value; // 安全取值
}
int val2 = a.GetValueOrDefault(); // 如果为 null 返回 0 (默认值)
int val3 = a ?? -1; // 如果为 null 返回 -1 (Null 合并运算符)
  • 运算：
    • 对可空类型进行算术运算时，如果任一操作数为 null，结果通常为 null。
    • 例如：int? c = a + b; 如果 b 是 null，则 c 也是 null。

3. C# 8.0 可空引用类型 (NRTs)

这是现代 .NET 开发的重点。在 .csproj 中开启 <Nullable>enable</Nullable> 后：

  • string 默认为非空。
  • string? 表示可能为空。
  • 作用：编译器会在编译期进行静态分析，如果你尝试将 null 赋给 string，或者在未判空的情况下使用 string?，编译器会发出警告（Warning）。
  • 注意：这不会改变运行时的 IL 代码，也不会阻止你在运行时赋 null 给非空字符串，它只是一个开发时的辅助工具。

4. 装箱行为

当可空值类型被装箱时：

  • 如果 HasValue 为 false，装箱结果为 null。
  • 如果 HasValue 为 true，装箱结果为内部值的装箱对象。
int? a = null;
object o = a; // o 是 null

int? b = 10;
object p = b; // p 是 boxed int (10)

💡面试延伸追问（预判面试官后续提问）

  1. int? 和 int 在内存中有什么区别？
    • 考点：int 占 4 字节；int? (Nullable<int>) 占 5 字节（4 字节值 + 1 字节 bool 标记），但由于内存对齐，通常也会占用 8 字节。
  2. 如何判断一个可空类型是否有值？直接 if (a != null) 可以吗？
    • 考点：可以。C# 编译器对 Nullable<T> 重载了 == 和 != 运算符，使其能像引用类型一样与 null 比较。但推荐使用 HasValue，语义更清晰且性能微优（避免运算符重载调用）。
  3. 可空引用类型（NRTs）开启后，为什么有时候还是会报 NullReferenceException？
    • 考点：因为 NRTs 只是编译期的静态分析警告，不是运行时的强制检查。如果使用了反射、反序列化、第三方库或者故意绕过编译器检查，运行时依然可能出现 null 引用异常。
  4. default(int?) 的值是什么？
    • 考点：是 null（即 HasValue 为 false 的 Nullable<int> 实例）。

五、什么是属性，什么是字段

✅面试简答（考场口述答案）

**字段（Field）**是类或结构体中直接存储数据的变量；**属性（Property）**是字段的访问器，它通过 get 和 set 方法提供对数据的受控访问。

  • 核心区别：
    1. 封装性：字段通常是 private 的，用于内部存储；属性通常是 public 的，用于对外暴露数据，并可以在赋值/取值时加入逻辑（如验证、懒加载）。
    2. 本质：字段是内存中的存储空间；属性在编译后会生成 get_XXX() 和 set_XXX() 两个方法。
    3. 最佳实践：C# 推荐永远不要公开公共字段，应始终使用属性来暴露数据，以保持 API 的稳定性和灵活性。

📚深入解析

1. 语法与底层实现

字段 (Field)

public class User
{
    // 字段：直接存储数据
    private string _name; 
}

属性 (Property)

public class User
{
    private string _name;

    // 属性：通过方法访问字段
    public string Name 
    { 
        get { return _name; } 
        set 
        { 
            if (string.IsNullOrEmpty(value)) throw new ArgumentException();
            _name = value; 
        } 
    }
}

自动属性 (Auto-Implemented Property) C# 3.0+ 引入了语法糖，编译器会自动生成一个隐藏的私有字段（Backing Field）。

public string Name { get; set; } 
// 编译后等同于上面的写法，只是字段名由编译器生成（如 <Name>k__BackingField）

2. 为什么推荐使用属性而不是公共字段？

这是面向对象设计的重要原则，原因如下：

  1. 数据验证与逻辑控制： 你可以在 set 中确保数据合法性（如年龄不能为负），在 get 中实现懒加载或计算逻辑。公共字段无法做到这一点。
  2. 二进制兼容性（Binary Compatibility）： 如果你发布了一个库，其中有一个公共字段 public int Age;。后来你想给 Age 加验证逻辑，必须把它改成属性。这会导致所有引用该库的程序集重新编译，否则它们会找不到字段而报错。 如果你一开始就使用属性，后续修改 get/set 内部的逻辑不需要重新编译调用方。
  3. 数据绑定支持： WPF、WinForms、ASP.NET Core 等框架的数据绑定机制通常只识别属性，不识别字段。
  4. 调试与监控： 你可以在属性的 get/set 中打断点，观察谁在读取或修改数据。字段很难做到这一点。
  5. 接口支持： 接口（Interface）可以定义属性，但不能定义字段。

3. 字段与属性的对比表

特性 字段 (Field) 属性 (Property)
存储 直接分配内存 通常关联一个隐藏字段，或通过逻辑计算
访问方式 直接读写 (obj.field) 通过方法调用 (obj.get_Property())
可见性 建议 private / protected 通常 public / internal
逻辑能力 无 可包含验证、通知、计算等逻辑
反射行为 FieldInfo PropertyInfo
序列化 大多数序列化器默认处理 大多数序列化器默认处理

4. 高级特性：Init-only 属性 (C# 9+) 

public string Name { get; init; }
  • init 允许属性只能在对象初始化器（new User { Name = "..." }）或构造函数中被赋值，之后变为只读。这比 readonly 字段更灵活，且支持不可变对象模式。

💡面试延伸追问（预判面试官后续提问）

  1. 什么是 Backing Field（后备字段）？什么时候需要显式定义它？
    • 考点：自动属性背后都有一个编译器生成的字段。当你需要在 get/set 中访问这个底层存储，或者需要进行复杂的验证逻辑时，就需要手动定义私有字段（通常命名为 _fieldName 或 fieldName）。
  2. 属性可以是虚的（Virtual）吗？字段可以吗？
    • 考点：属性可以是 virtual 的，子类可以重写 get 或 set 逻辑。字段不可以是 virtual 的，因为字段代表的是内存位置，不支持多态。
  3. const 和 static readonly 以及“只读属性”有什么区别？
    • 考点：
      • const：编译时常量，嵌入 IL。
      • static readonly：运行时常量，静态初始化。
      • readonly 字段：实例级别的运行时常量，只能在构造函数赋值。
      • { get; } 属性：可以在构造函数或初始化器中赋值，更灵活，支持表达式体。
  4. 在 EF Core 中，为什么有时候建议使用私有字段配合属性映射？
    • 考点：为了保持领域模型的纯洁性（Encapsulation）。有些状态只应在内部通过业务方法修改，不应对外公开 set，但 EF Core 可以通过配置访问私有字段来进行持久化。

六、什么是泛型

✅面试简答（考场口述答案）

泛型（Generics）是 C# 2.0 引入的核心特性，它允许在定义类、接口或方法时使用类型占位符（如 <T>），直到实例化或调用时才指定具体的数据类型。

  • 核心优势：
    1. 类型安全：编译时检查类型，避免了运行时因类型转换错误导致的异常。
    2. 性能提升：对于值类型，泛型避免了**装箱（Boxing）和拆箱（Unboxing）**的开销。
    3. 代码复用：一套逻辑可以处理多种数据类型，无需为 int、string 等分别写重复代码。
  • 典型应用：集合类（List<T>, Dictionary<TKey, TValue>）、LINQ、依赖注入容器。

📚深入解析

1. 为什么需要泛型？（对比非泛型）

在泛型出现之前，我们使用 ArrayList 或 object 来存储任意类型：

// ❌ 非泛型方式 (ArrayList)
ArrayList list = new ArrayList();
list.Add(1);      // 发生装箱：int -> object
list.Add("Hello"); // 合法，但破坏了类型一致性

int num = (int)list[0]; // 发生拆箱：object -> int，且需要强制转换
// int str = (int)list[1]; // 运行时抛出 InvalidCastException！

使用泛型后：

// ✅ 泛型方式 (List<T>)
List<int> list = new List<int>();
list.Add(1);      // 直接存储 int，无装箱
// list.Add("Hello"); // 编译错误！类型不安全

int num = list[0]; // 直接获取 int，无拆箱，无需强转

2. 底层原理：代码共享与特化

  • 引用类型：所有引用类型（class）的泛型实例在 JIT 编译后共享同一份本机代码。因为引用本质上都是指针（4字节或8字节），操作逻辑一致。
  • 值类型：每个不同的值类型（int, double, struct）泛型实例都会生成一份独立的本机代码。这是因为值类型的大小和内存布局不同，JIT 必须为每种值类型生成特定的优化代码。这也是泛型高性能的关键原因。

3. 泛型约束 (Constraints)

为了在泛型内部使用特定功能（如比较大小、创建实例），我们需要对 T 进行限制：

约束 语法 含义
引用类型 where T : class T 必须是引用类型
值类型 where T : struct T 必须是值类型（含 Nullable）
构造函数 where T : new() T 必须有公共无参构造函数
基类 where T : BaseClass T 必须继承自 BaseClass
接口 where T : IInterface T 必须实现 IInterface 
public class Repository<T> where T : Entity, new()
{
    public T Create()
    {
        return new T(); // 只有加了 new() 约束才能这样写
    }
}

4. 协变与逆变 (Covariance & Contravariance)

这是高阶考点，主要针对接口和委托：

  • 协变 (out T)：允许将 IEnumerable<Derived> 赋值给 IEnumerable<Base>。适用于只读场景（输出）。
  • 逆变 (in T)：允许将 Action<Base> 赋值给 Action<Derived>。适用于只写场景（输入）。
  • 注意：List<T> 是不变的（Invariant），因为它既可读又可写，为了保证类型安全，不允许协变/逆变。

💡面试延伸追问（预判面试官后续提问）

  1. 泛型是如何解决装箱问题的？
    • 考点：泛型在 JIT 编译时会生成针对特定类型的代码。对于 List<int>，内部数组直接存储 int 的二进制数据，而不是 object 引用，因此完全避开了堆分配和拷贝过程。
  2. typeof(List<int>) 和 typeof(List<string>) 是同一个 Type 吗？
    • 考点：不是。虽然它们共享元数据定义，但在运行时它们是不同类型的对象。可以通过 GetGenericTypeDefinition() 获取它们的通用定义 List<>。
  3. 什么是开放类型（Open Type）和封闭类型（Closed Type）？
    • 考点：
      • 开放类型：包含未指定的类型参数，如 List<T> 或 Dictionary<,>。不能实例化。
      • 封闭类型：所有类型参数都已指定，如 List<int>。可以实例化。
  4. 泛型方法可以重载吗？
    • 考点：可以，但不能仅通过改变类型参数的名称来重载。必须通过参数列表的不同（数量或类型）来区分。例如 void Do<T>() 和 void Do<T>(T item) 是合法的重载。

七、const和readonly修饰符的区别是什么

✅面试简答（考场口述答案）

const 和 readonly 都用于定义不可变的值，但核心区别在于赋值时机和编译行为：

  1. 赋值时机：
    • const：必须在声明时初始化，是编译时常量。
    • readonly：可以在声明时或构造函数中初始化，是运行时常量。
  2. 支持类型：
    • const：仅限基元类型（int, double, bool 等）、string 或 null。不能是自定义类或结构体（除非为 null）。
    • readonly：可以是任何类型，包括复杂的对象、数组、自定义类。
  3. 底层实现与版本控制：
    • const：值会被直接嵌入到调用方的 IL 代码中。如果修改了 const 值但未重新编译引用项目，会导致数据不一致。
    • readonly：通过字段访问，修改后只需重新编译定义方，引用方无需重新编译。

一句话总结：const 是硬编码在程序里的死值，readonly 是运行时确定的只读字段。

📚深入解析

1. 详细对比表

特性 const (编译时常量) readonly (运行时常量)
初始化时机 声明时必须赋值 声明时 或 构造函数中
修饰符限制 隐式 static，不能再加 static 可以是实例成员，也可以是 static readonly
数据类型 基元类型、string、enum、null 任意类型 (包括对象、集合)
IL 表现 值直接替换到调用处 (Literal) 生成字段，通过 ldfld 指令读取
性能 极快（无内存访问开销） 稍慢（需访问内存字段），但差异微乎其微
反射支持 无法通过反射修改 可以通过反射强制修改（不推荐）

2. 代码示例 

public class Config
{
    // ✅ Const: 编译时确定，隐含 static
    public const double Pi = 3.14159; 
    public const string AppName = "MyApp";

    // ✅ Readonly: 运行时确定，可以是实例级别
    public readonly DateTime CreatedAt;
    public readonly List<string> Tags;

    public Config()
    {
        CreatedAt = DateTime.Now; // 允许在构造函数赋值
        Tags = new List<string> { "C#", ".NET" }; // 允许复杂对象
    }

    // ❌ 错误: Const 不能在构造函数赋值
    // public const int MaxRetries; 
}

3. 关键陷阱：版本控制问题（高频考点）

这是 const 最大的坑。假设你有两个项目：Library.dll 和 App.exe。

  • 场景：

    1. Library 中定义：public const int Version = 1;
    2. App 引用 Library 并调用：Console.WriteLine(Library.Version);
    3. 编译 App。此时，App.exe 的 IL 代码中，Version 的位置直接被替换成了数字 1。
    4. 后来你修改 Library：public const int Version = 2; 并重新编译 Library.dll，但没有重新编译 App.exe。
    5. 运行 App.exe：输出依然是 1！因为 App.exe 根本不去读 Library.dll 里的值，它用的是自己肚子里的“备份”。

  • 解决方案：如果某个常量未来可能会变，或者会被其他项目引用，务必使用 public static readonly 代替 const。

4. readonly 对象的不可变性误区

readonly 只能保证引用本身不被修改，不能保证引用指向的对象内容不被修改。

public class MyClass
{
    public readonly List<int> Numbers = new List<int>();
}

var obj = new MyClass();
// obj.Numbers = new List<int>(); // ❌ 编译错误：不能修改 readonly 字段引用
obj.Numbers.Add(10);             // ✅ 合法：可以修改列表内部的内容！

如果需要真正的不可变对象，应使用 ImmutableList<T> 或将类设计为不可变类。

💡面试延伸追问（预判面试官后续提问）

  1. static readonly 和 const 选哪个？
    • 考点：除非是绝对不可能改变的值（如数学常数 Pi、物理常数），否则推荐使用 static readonly。它在保持只读语义的同时，避免了 const 的版本部署陷阱，且支持更多数据类型。
  2. readonly 字段可以在普通方法中赋值吗？
    • 考点：不可以。只能在声明时或构造函数（包括静态构造函数对应 static readonly）中赋值。一旦对象构造完成，readonly 字段就不可再赋值。
  3. 什么是“常量折叠”（Constant Folding）？
    • 考点：编译器优化技术。当表达式中只包含 const 常量时，编译器会在编译期直接计算出结果。例如 const int a = 2; const int b = 3; int c = a + b;，编译器会直接把 c 赋值为 5，而不生成加法指令。
  4. C# 10 引入的 required 关键字和 readonly 有什么关系？
    • 考点：required 确保属性在初始化时被赋值，常与 init 或 readonly 配合使用，用于构建不可变对象（Immutable Objects），确保对象一旦创建状态即固定。

八、ref和out关键字的区别是什么

✅面试简答（考场口述答案）

ref 和 out 都用于通过引用传递参数，允许方法修改调用方变量的值。核心区别在于初始化责任和使用意图：

  1. 初始化要求：
    • ref：变量在传递给方法之前必须已初始化。方法内部可以读也可以写。
    • out：变量在传递前不需要初始化。方法内部必须在返回前对其赋值，且通常不能在赋值前读取它。
  2. 语义意图：
    • ref：侧重于“双向通信”，既传入数据又传出修改后的结果（如交换两个数）。
    • out：侧重于“输出结果”，常用于一个方法需要返回多个值的场景（如 int.TryParse）。
  3. 调用语法：C# 7.0+ 允许在调用时直接声明 out 变量（如 TryParse(s, out int result)），而 ref 必须传入已存在的变量。

📚深入解析

1. 代码对比示例

Ref 示例：

public void ModifyValue(ref int number)
{
    // 可以读取原始值
    Console.WriteLine($"Original: {number}"); 
    // 修改值
    number = 100; 
}

// 调用
int a = 10; // ✅ 必须先初始化
ModifyValue(ref a);
Console.WriteLine(a); // 输出: 100

Out 示例：

public bool TryGetResult(out int result)
{
    // ❌ 错误：不能在赋值前读取 out 参数
    // Console.WriteLine(result); 
    
    result = 42; // ✅ 必须在方法结束前赋值
    return true;
}

// 调用
int b; // ✅ 不需要初始化
if (TryGetResult(out b))
{
    Console.WriteLine(b); // 输出: 42
}

2. 底层原理

  • 内存层面：两者在 IL（中间语言）层面非常相似，都是通过传递变量的内存地址（指针）来实现的。
  • 编译器检查：区别主要在于 C# 编译器的静态分析规则。out 强制编译器确保方法内所有路径都对变量进行了赋值，否则报错。这保证了调用方拿到的永远是一个有效的值。

3. 常见应用场景

  • out 的经典用法：
    • int.TryParse(string, out int)：尝试转换，成功则输出结果。
    • Dictionary.TryGetValue(key, out value)：尝试获取值，避免 KeyNotFoundException。
    • 这种模式被称为 Try-Parse 模式，是处理可能失败的操作并返回结果的标准做法。
  • ref 的经典用法：
    • 高性能场景下传递大型结构体（struct），避免拷贝开销（C# 7.2+ 推荐结合 readonly ref 使用以保证安全）。
    • 需要修改调用方状态的场景（如 Interlocked.Exchange）。

4. C# 7.0+ 的新特性

  • Out 变量声明：可以在方法调用的参数列表中直接声明变量，简化代码。 
    // 旧写法
int result;
int.TryParse("123", out result);

// 新写法
int.TryParse("123", out int result);
  • Ref Locals & Ref Returns：方法可以返回一个 ref，允许调用者直接修改数组或对象内部的元素，实现零拷贝的高性能操作。

💡面试延伸追问（预判面试官后续提问）

  1. ref 和 out 能用于重载方法吗？
    • 考点：不能。编译器认为 ref 和 out 在元数据签名中是相同的（都是按地址传递）。如果只有这两个关键字不同，会报编译错误 CS0663。必须配合其他参数类型的不同才能重载。
  2. 为什么 out 参数在方法内部赋值前不能读取？
    • 考点：因为调用方传入的可能是一个未初始化的垃圾值。为了保证类型安全和逻辑正确，C# 强制要求方法必须先赋予其一个确定的值，之后才能被视为有效变量使用。
  3. 什么是 in 参数？它和 ref 有什么区别？
    • 考点：in 也是按引用传递，但它是只读的。主要用于高性能场景传递大型结构体，避免拷贝的同时防止方法内部意外修改数据。它是 ref readonly 的语法糖。
  4. 在异步方法（async）中可以使用 ref 或 out 吗？
    • 考点：不可以。因为异步方法在执行过程中可能会切换线程或暂停，栈帧可能会消失，导致引用地址失效。如果需要类似功能，应返回一个包含结果的元组（Tuple）或自定义对象。

九、接口和抽象类的区别是什么

✅面试简答（考场口述答案）

接口（Interface）和抽象类（Abstract Class）都用于实现抽象和多态，但核心区别在于设计意图和继承机制：

  1. 本质区别：
    • 抽象类是对“事物”的抽象，表示 “Is-a” 关系（是什么）。它包含成员的实现细节和状态（字段）。
    • 接口是对“行为”的抽象，表示 “Can-do” 关系（能做什么）。它主要定义契约，通常不包含状态。
  2. 继承限制：
    • 类只能继承一个抽象类（单继承）。
    • 类可以实现多个接口（多实现）。
  3. 成员支持：
    • 抽象类可以有字段、构造函数、非抽象方法（具体实现）。
    • 接口不能有实例字段和构造函数（C# 8.0 前不能有实现，C# 8.0+ 支持默认实现但仍无状态）。

一句话总结：如果你需要共享代码和状态，用抽象类；如果你需要定义跨层级的行为契约或多重能力，用接口。

📚深入解析

1. 详细对比表

特性 抽象类 (Abstract Class) 接口 (Interface)
继承方式 class Child : Base (单继承) class Child : IBase (多实现)
构造函数 ✅ 支持 ❌ 不支持
字段 (Fields) ✅ 支持 (可存状态) ❌ 不支持 (C# 8+ 仅支持静态常量)
访问修饰符 可以是 public, protected, internal 等 默认为 public，不能显式指定 (C# 8+ 部分成员可私有)
方法实现 可以包含具体实现的方法 C# 8.0 前纯抽象；C# 8.0+ 支持默认实现
性能 略快 (虚方法调用) 略慢 (接口调用需查找分发表，但在 JIT 优化下差异极小)
版本控制 容易扩展 (添加新方法不影响子类) 难扩展 (添加新方法会破坏所有实现类，除非用默认实现)

2. 设计哲学：Is-a vs Can-do

  • 抽象类 (Is-a)：
    • 场景：Dog is an Animal。
    • 特点：它们共享相同的底层结构和逻辑。比如 Animal 类可能有 HeartBeat() 的具体实现，所有动物都一样。
  • 接口 (Can-do)：
    • 场景：Bird can Fly, Plane can Fly。
    • 特点：它们属于完全不同的类别，但具备相同的能力。接口不关心你是谁，只关心你能做什么。

3. C# 8.0 的重大变化：默认接口实现

在 C# 8.0 之前，接口修改是灾难性的（Breaking Change）。现在接口可以包含默认实现：

public interface ILogger
{
    void Log(string message); // 必须由实现类提供
    
    // 默认实现：如果实现类不提供 LogWarning，则使用此逻辑
    default void LogWarning(string message) 
    {
        Log($"[WARNING] {message}");
    }
}
  • 注意：即使有默认实现，接口依然不能拥有实例字段。这意味着默认实现不能依赖对象的状态，只能依赖其他接口方法或静态数据。

4. 什么时候选哪个？

  • 选抽象类：
    • 多个相关类共享大量通用代码。
    • 你需要控制子类的内部状态（通过 protected 字段）。
    • 你需要提供构造函数来强制初始化逻辑。
  • 选接口：
    • 你需要让不相关的类具备相同的功能（如 ISerializable, IComparable）。
    • 你需要多重继承的行为。
    • 你正在设计插件系统或解耦架构（依赖倒置原则 DIP 通常依赖接口）。

💡面试延伸追问（预判面试官后续提问）

  1. 如果一个类既继承了抽象类又实现了接口，且两者有同名方法，会发生什么？
    • 考点：类必须提供该方法的实现。如果抽象类中该方法已是具体实现（非 abstract），则直接继承；如果是 abstract，则类必须重写。接口的默认实现会被类的具体实现覆盖。
  2. 什么是显式接口实现（Explicit Interface Implementation）？有什么用？
    • 考点：语法 void IMyInterface.Method() { ... }。
    • 作用：
      1. 解决不同接口间同名方法的冲突。
      2. 隐藏接口成员，使其只能通过接口引用访问，而不能通过类实例访问（降低 API 复杂度）。
  3. 抽象类可以有静态成员吗？接口可以有静态成员吗？
    • 考点：抽象类完全可以。C# 8.0+ 的接口也可以有静态成员（包括静态字段和方法），甚至可以有静态构造函数，但这主要用于辅助默认接口方法的实现，而非存储实例状态。
  4. 为什么 C# 不支持类的多重继承，却支持接口的多重实现？
    • 考点：多重继承会导致“菱形问题”（Diamond Problem），即两个基类有同名方法时，子类不知道该继承哪一个，且涉及复杂的内存布局（多个 vtable）。接口没有状态（字段），只有方法签名，因此不存在内存布局冲突，编译器只需合并方法分发表即可。

十、什么是多态性

✅面试简答（考场口述答案）

**多态性（Polymorphism）**是面向对象编程的三大核心特性之一，指“同一个接口，不同的实现”。它允许我们使用基类引用指向子类对象，并在运行时根据对象的实际类型调用相应的方法。

  • 核心实现：主要通过继承、**虚方法（virtual/override）和接口（interface）**来实现。
  • 两种形式：
    1. 编译时多态（静态多态）：通过**方法重载（Overloading）**实现，编译器在编译阶段确定调用哪个方法。
    2. 运行时多态（动态多态）：通过**方法重写（Overriding）**实现，CLR 在运行阶段根据对象的实际类型决定调用哪个方法（这是面试考察的重点）。
  • 价值：提高代码的扩展性和可维护性，符合开闭原则（OCP）。

📚深入解析

1. 运行时多态的本质：虚方法表（V-Table）

当你在 C# 中定义一个 virtual 方法并在子类中 override 它时，CLR 会为每个包含虚方法的类创建一个虚方法表（Virtual Method Table, V-Table）。

  • 过程：
    1. 每个对象实例的头部都有一个指针（Type Handle），指向其类型的 V-Table。
    2. V-Table 中存储了该类所有虚方法的实际地址。
    3. 当你调用 baseRef.VirtualMethod() 时，CLR 不会直接跳转到基类的代码，而是：
      • 通过对象找到它的 V-Table。
      • 在 V-Table 中查找该方法对应的最新地址（即子类重写的地址）。
      • 跳转到该地址执行。

这就是为什么“基类引用指向子类对象”时，调用的是子类方法的原因。

2. 代码示例 

public class Animal
{
    // 虚方法：允许子类重写
    public virtual void Speak()
    {
        Console.WriteLine("Animal makes a sound");
    }
}

public class Dog : Animal
{
    // 重写：提供特定实现
    public override void Speak()
    {
        Console.WriteLine("Woof!");
    }
}

public class Cat : Animal
{
    public override void Speak()
    {
        Console.WriteLine("Meow!");
    }
}

// 多态调用
public void MakeSound(Animal animal)
{
    // 编译时：animal 的类型是 Animal
    // 运行时：如果传入的是 Dog，调用 Dog.Speak(); 如果是 Cat，调用 Cat.Speak()
    animal.Speak(); 
}

3. 编译时多态 vs 运行时多态

特性 编译时多态 (Overloading) 运行时多态 (Overriding)
实现方式 方法重载（同名不同参） 虚方法重写（virtual/override）
绑定时间 编译期（静态绑定） 运行期（动态绑定）
性能 稍快（直接跳转） 稍慢（需查 V-Table，但现代 JIT 优化极好）
灵活性 低 高，支持插件化架构

4. 接口实现的多态

接口是多态的另一种重要形式。由于接口没有实现细节，所有接口方法的调用本质上都是动态绑定的。

public interface IPrintable
{
    void Print();
}

public class Document : IPrintable { public void Print() { ... } }
public class Photo : IPrintable { public void Print() { ... } }

// 统一处理
void Process(IPrintable item) { item.Print(); }

💡面试延伸追问（预判面试官后续提问）

  1. virtual、abstract 和 override 有什么区别？
    • 考点：
      • virtual：有默认实现，子类可选择性重写。
      • abstract：无实现，子类必须重写。
      • override：用于替换基类的 virtual 或 abstract 方法。
  2. 如果子类中没有 override，而是用了 new 关键字隐藏基类方法，还能实现多态吗？
    • 考点：不能。new 是静态绑定。如果基类引用指向子类对象，调用的依然是基类的方法。多态的核心是动态绑定，new 破坏了这一链条。
  3. 什么是“里氏替换原则”（LSP）？它和多态有什么关系？
    • 考点：LSP 要求子类对象能够替换父类对象而不影响程序的正确性。多态是实现 LSP 的技术手段，而 LSP 是使用多态时必须遵守的设计约束。如果子类重写了方法但改变了基类的契约（如抛出异常或改变返回值语义），就违反了 LSP。
  4. JIT 编译器如何优化虚方法调用？
    • 考点：虽然虚调用需要查表，但 JIT 会使用内联缓存（Inline Caching）或守护内联（Guarded Inlining）。如果 JIT 发现某个虚方法在绝大多数情况下都指向同一个具体类型，它会直接内联该方法的代码并添加一个快速类型检查，从而消除虚调用的开销。
