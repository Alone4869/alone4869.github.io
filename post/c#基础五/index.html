一、什么是可空引用类型

✅面试简答（考场口述答案）

可空引用类型（Nullable Reference Types, NRT） 是 C# 8.0 引入的一项编译时特性，旨在从代码层面减少 NullReferenceException。

它的核心机制是将引用类型分为两类：

  1. 非空引用类型（如 string）：编译器假定它永远不会为 null，如果赋值为 null 或可能为 null 的值，会发出警告。
  2. 可空引用类型（如 string?）：显式声明该变量可以为 null，访问其成员前必须进行 null 检查。

注意：这只是一个静态分析工具，运行时 CLR 并不区分两者，不会阻止你给 string 赋值 null，但会在编译阶段通过警告提示潜在风险。

📚深入解析

1. 为什么需要 NRT？

在 C# 8.0 之前，所有的引用类型都可以为 null，导致了著名的“十亿美元错误”（Tony Hoare 语）。开发者经常忘记检查 null，导致生产环境抛出 NullReferenceException。NRT 通过编译器的静态分析，强制开发者思考“这个值是否可能为空”。

2. 如何启用？

在项目文件 .csproj 中配置：

<PropertyGroup>
    <Nullable>enable</Nullable>
</PropertyGroup>

或者在文件顶部使用指令：

#nullable enable

3. 核心语法与行为

类型声明 含义 编译器行为
string s 非空引用 赋值为 null 时报警告；作为参数传递时假定不为 null
string? s 可空引用 允许赋值为 null；访问成员前需检查 null，否则报警告
T (泛型) 取决于上下文 若未约束，默认为可空；若约束 where T : notnull 则不可空

4. 代码示例 

#nullable enable

public class UserService 
{
    public string GetUserName(int id) 
    {
        // ❌ 警告：返回可能为 null 的表达式，但返回类型是非空 string
        // return FindUser(id)?.Name; 
        
        // ✅ 正确做法：处理 null 情况
        var user = FindUser(id);
        return user?.Name ?? "Unknown"; 
    }

    public void PrintName(string? name) 
    {
        // ❌ 警告：'name' 可能为 null
        // Console.WriteLine(name.Length); 

        // ✅ 正确做法：先检查
        if (name != null) 
        {
            Console.WriteLine(name.Length);
        }
        
        // 或者使用 null 合并运算符
        Console.WriteLine(name?.Length ?? 0);
    }

    private User? FindUser(int id) 
    {
        // 模拟数据库查询，可能返回 null
        return null; 
    }
}

public class User 
{
    public string Name { get; set; } = ""; // 初始化以避免警告
}

5. 关键特性：空状态静态分析

编译器会跟踪变量的“空状态”（Null State）：

  • NotNull：确定不为 null。
  • MaybeNull：可能为 null。
  • NotNullWhen：通过方法属性标注，告诉编译器某个参数在方法返回 true 时不为 null。
// 告诉编译器：如果返回 true，则 name 一定不为 null
public static bool TryGetName(object? obj, [NotNullWhen(true)] out string? name) 
{
    if (obj is User user && user.Name != null) 
    {
        name = user.Name;
        return true;
    }
    name = null;
    return false;
}

6. 常见警告及消除方法

  • CS8600: 将 null 字面量或可能的 null 值转换为非空类型。
  • CS8602: 解引用可能为 null 的引用。
  • CS8618: 非空字段未在构造函数中初始化。
    • 解决方法：使用默认值初始化、使用 ! 抑制符（谨慎使用）、或使用 [Required] 特性。

⚠️ 关于 ! 抑制符：name!.Length 告诉编译器“我保证这里不为 null，别报错了”。滥用会导致 NRT 失效，应仅在确实比编译器更了解上下文时使用。

💡面试延伸追问（预判面试官后续提问）

  1. NRT 是运行时检查吗？如果我给非空 string 赋值 null，程序会崩溃吗？

    • 考点：NRT 仅是编译时静态分析，运行时 CLR 不感知。赋值 null 不会立即崩溃，但在后续解引用时会抛出 NullReferenceException。

  2. 如何处理第三方库没有开启 NRT 的情况？

    • 考点：第三方库的类型可能被编译器视为“ oblivious ”（模糊状态），既不完全可信也不完全报错。可以通过封装、适配器模式或手动添加 null 检查来处理。

  3. 泛型中的 where T : class 和 where T : notnull 有什么区别？

    • 考点：class 允许 nullable 引用类型（如 string?），而 notnull 禁止任何 null 值（包括可空引用类型和可空值类型），约束更严格。

  4. 在 ASP.NET Core 控制器中，如何优雅地处理模型绑定的 null 值？

    • 考点：结合 [BindRequired]、数据注解验证（Data Annotations）、以及全局异常处理中间件。

二、什么是CIL、CLR、CLI、CTS

✅面试简答（考场口述答案）

这四个概念是 .NET 平台的核心架构组成部分，它们之间的关系可以概括为：

  • CLI (Common Language Infrastructure)：通用语言基础结构。它是 ECMA/ISO 的国际标准规范，定义了 .NET 平台的整体架构和运行环境标准。
  • CLR (Common Language Runtime)：公共语言运行时。它是微软对 CLI 标准的具体实现，负责代码的执行、内存管理（GC）、异常处理、线程调度等。
  • CIL (Common Intermediate Language)：通用中间语言（旧称 MSIL）。C# 等高级语言编译后生成的中间代码，不是机器码，由 CLR 在运行时通过 JIT 编译器转换为本地机器码。
  • CTS (Common Type System)：通用类型系统。它定义了所有 .NET 语言必须遵循的数据类型规范，确保不同语言（如 C# 和 VB.NET）编写的代码可以互相调用（互操作性）。

一句话总结： CLI 是标准，CLR 是实现，CIL 是中间代码，CTS 是类型规范。

📚深入解析

为了更清晰地理解，我们可以从 .NET 程序的编译和执行流程来看这四个概念的作用：

1. CLI (Common Language Infrastructure) - 标准规范

  • 性质：它不是一个软件，而是一份文档/标准（ECMA-335）。
  • 作用：它规定了如何构建一个跨语言的执行环境。任何厂商（如微软、Mono、Unity）只要遵循 CLI 标准，就可以开发自己的 .NET 运行时。
  • 包含内容：CLI 标准中包含了 CTS、CLS（公共语言规范）、VES（虚拟执行系统，即运行时引擎）和元数据规范。

2. CTS (Common Type System) - 类型统一

  • 问题背景：C# 有 int，VB.NET 有 Integer，C++ 有 int32。如果没有统一标准，不同语言写的 DLL 无法互相识别类型。
  • 作用：CTS 定义了在运行时环境中支持的数据类型和操作。
    • 例如：CTS 规定所有整数最终都映射为 System.Int32。
    • 它定义了值类型（Value Types）和引用类型（Reference Types）的行为。
  • 价值：实现了跨语言集成。你用 C# 写的一个类库，可以被 VB.NET 或 F# 直接引用，因为它们的类型在底层是一致的。

3. CIL (Common Intermediate Language) - 中间代码

  • 编译过程：当你编译 C# 代码时，编译器（Roslyn）不会直接生成 CPU 能执行的机器码（如 x86/x64 指令），而是生成 CIL 代码。
  • 特点：
    • 平台无关性：CIL 不依赖具体的 CPU 架构。
    • 包含元数据：CIL 程序集（.dll/.exe）中不仅包含指令，还包含完整的类型信息（元数据），这使得反射（Reflection）成为可能。
  • 执行：当程序运行时，CLR 中的 JIT (Just-In-Time) 编译器 会将 CIL 动态编译成当前机器的本地机器码。

4. CLR (Common Language Runtime) - 运行时引擎

  • 地位：它是 .NET 应用程序的“操作系统”，是微软对 CLI 中 VES（虚拟执行系统）的具体实现。
  • 核心职责：
    1. 加载代码：加载程序集和 CIL 代码。
    2. JIT 编译：将 CIL 转为本地机器码。
    3. 内存管理：负责对象的分配和垃圾回收（GC）。
    4. 安全性检查：验证代码类型安全（Type Safety）。
    5. 异常处理与线程管理。

关系图解 

  graph TD
    A[C#/VB.NET/F#源码] -->|编译| B[CIL+元数据]
    B -->|输出| H[程序集 dll/exe]
    H -->|加载| C[CLR运行时]

    D[CLI标准规范] -.->|定义架构| C

💡面试延伸追问（预判面试官后续提问）

  1. CIL 和机器码有什么区别？为什么 .NET 要先编译成 CIL 而不是直接编译成机器码？
    • 考点：跨平台能力、JIT 优化、启动速度 vs 运行速度的权衡。
  2. CTS 和 CLS (Common Language Specification) 有什么区别？
    • 考点：CTS 是底层所有类型的集合，CLS 是 CTS 的子集，是所有 .NET 语言都必须支持的最小功能集，以确保最大的互操作性。
  3. .NET Core / .NET 5+ 中还有 CLR 吗？
    • 考点：术语的变化。在 .NET Core 中，运行时通常被称为 “CoreCLR”，但架构理念依然遵循 CLI 标准。面试官可能在考察你对新旧 .NET 架构演变的了解。
  4. JIT 编译的过程是怎样的？什么是 NGen (Native Image Generator) 或 R2R (Ready to Run)？
    • 考点：性能优化。JIT 是在运行时编译，NGen/R2R 是提前编译部分 CIL 为机器码以减少启动时间。

三、C#和.NET的区别是什么

✅面试简答（考场口述答案）

C# 是编程语言，.NET 是开发平台（运行时环境/框架）。

  • C#：是一种强类型、面向对象的编程语言，由微软设计，遵循 ECMA 标准。它负责编写逻辑代码，最终被编译成中间语言（CIL）。
  • .NET：是一个免费的、跨平台的开发者平台，包含类库（BCL/FCL）、运行时（CLR/CoreCLR）和工具链。它负责执行 C# 编译后的代码，提供内存管理、IO、网络等基础能力。

类比：C# 就像“英语”，而 .NET 就像“使用英语交流的社会环境和规则”。你可以用英语（C#）在 .NET 环境下写作，也可以用其他语言（如 F#、VB.NET）在这个环境下写作。

📚深入解析

很多初学者容易混淆这两个概念，因为它们在微软生态中绑定得非常紧密。我们可以从以下几个维度区分：

1. 本质不同

  • C# (Language)：
    • 属于语法层。
    • 定义了变量怎么声明、循环怎么写、类怎么继承、异步怎么用 (async/await)。
    • 编译器叫 Roslyn，它将 .cs 文件编译成 .dll 或 .exe（包含 CIL 和元数据）。
  • .NET (Platform/Framework)：
    • 属于运行层和库层。
    • 提供了 System.String, System.Console, List<T> 等成千上万个现成的类。
    • 提供了 CLR (Common Language Runtime) 来加载代码、进行 JIT 编译、垃圾回收 (GC)。

2. 多对一关系

  • .NET 支持多种语言：虽然 C# 是最主流的，但 .NET 平台同样完美支持 F# (函数式)、VB.NET、C++/CLI 等。这些语言编写的代码可以互相引用，因为它们都遵循 .NET 的 CTS (通用类型系统)。
  • C# 也可以脱离传统 .NET Framework：虽然少见，但理论上 C# 编译器可以生成针对其他运行时的代码（如 Unity 的 IL2CPP，或者早期的 Mono），但在现代后端开发中，C# 几乎总是与 .NET (Core/5/6/7/8) 绑定出现。

3. 版本迭代独立

  • C# 版本：C# 1.0, 2.0 … 10.0, 11.0, 12.0。新特性如 record, pattern matching, nullable reference types 是语言层面的升级。
  • .NET 版本：.NET Framework 4.8, .NET Core 3.1, .NET 5, 6, 7, 8, 9。新特性如 Minimal API, Performance improvements in GC, HTTP/3 support 是平台和运行时层面的升级。
  • 注意：通常新的 .NET 版本会支持最新的 C# 版本，但它们是分别发布的。

4. 历史演变 (.NET Framework vs .NET Core vs .NET 5+)

  • .NET Framework：仅限 Windows，闭源（部分开源），重量级。
  • .NET Core：跨平台（Windows/Linux/macOS），开源，轻量级，高性能。
  • .NET 5/6/7/8…：微软统一了平台，去掉了 “Core” 后缀，简称 “.NET”。这是目前面试中默认的 “.NET” 含义。

💡面试延伸追问（预判面试官后续提问）

  1. 既然 .NET 支持多种语言，为什么企业大多选择 C#？
    • 考点：生态丰富度、语法简洁性、社区支持、Visual Studio 的完美集成、就业市场主流。
  2. .NET Framework 和 .NET Core (现在的 .NET 5+) 有什么核心区别？
    • 考点：跨平台能力、性能差异（Core 更快）、微服务支持、部署方式（Framework 依赖安装，Core 可独立部署）。
  3. C# 代码是如何在 .NET 平台上运行起来的？请简述流程。
    • 考点：源码 -> Roslyn 编译器 -> CIL (中间语言) + 元数据 -> 程序集 (Assembly) -> CLR 加载 -> JIT 编译为机器码 -> CPU 执行。
  4. 什么是 BCL (Base Class Library) 和 FCL (Framework Class Library)？
    • 考点：BCL 是 .NET 最核心的基础类库（如 System, System.IO），所有 .NET 应用都必须依赖；FCL 是更上层的扩展库（如 ASP.NET Core, WPF, EF Core），按需引用。

四、值类型和引用类型有什么区别

✅面试简答（考场口述答案）

核心区别在于内存分配位置和数据访问方式：

  1. 内存位置：
    • 值类型（如 int, struct）通常分配在**栈（Stack）**上（作为局部变量时），或者内联存储在引用类型的内部。
    • 引用类型（如 class, interface, delegate）的对象实例分配在堆（Heap）上，栈中只存储指向堆内存的地址（引用）。
  2. 赋值行为：
    • 值类型赋值是拷贝数据。修改副本不影响原值。
    • 引用类型赋值是拷贝地址。多个变量指向同一块堆内存，修改其中一个会影响其他所有指向该对象的变量。
  3. 生命周期管理：
    • 值类型随作用域结束自动释放（出栈）。
    • 引用类型由 GC（垃圾回收器） 负责回收。

📚深入解析

1. 常见类型分类

特性 值类型 (Value Types) 引用类型 (Reference Types)
关键字 struct, enum class, interface, delegate, record (引用型)
内置类型 int, float, bool, char, decimal, DateTime, Guid string, object, dynamic, array[], List<T>
默认值 0, false, null (nullable) null
继承性 隐式继承自 System.ValueType，不能被继承 可继承其他类（单继承），实现接口
空值处理 不能为 null（除非使用 Nullable<T> / int?） 可以为 null

2. 内存布局详解（关键点）

  • 栈（Stack）：线程私有，内存连续，分配和释放速度极快（只需移动指针）。适合存储生命周期短、大小固定的数据。
  • 堆（Heap）：进程共享，内存不连续，分配较慢，需要 GC 维护。适合存储大型对象或生命周期不确定的对象。

注意陷阱：

  • 引用类型中的值类型字段：如果一个 class 里有一个 int 字段，这个 int 是存储在堆上的，因为它属于该对象的一部分。
  • 值类型中的引用类型字段：如果一个 struct 里有一个 string 字段，struct 本身可能在栈上，但 string 的内容依然在堆上，struct 里只存了那个字符串的地址。

3. 赋值与传递机制示例 

// 值类型演示
int a = 10;
int b = a; // 拷贝数值：b = 10
b = 20;    // 修改 b
Console.WriteLine(a); // 输出 10 (a 不受影响)

// 引用类型演示
var obj1 = new MyClass { Id = 1 };
var obj2 = obj1; // 拷贝地址：obj2 指向 obj1 同一块堆内存
obj2.Id = 2;     // 修改堆内存中的数据
Console.WriteLine(obj1.Id); // 输出 2 (obj1 也变了)

4. 性能考量

  • 值类型：由于分配在栈上且无需 GC，通常性能更高，缓存友好（Cache Friendly）。适合小型数据结构（如坐标点 Point）。
  • 引用类型：涉及堆分配和 GC 压力。频繁创建小型引用类型对象会导致 GC 频繁触发，影响性能。这也是为什么 C# 9 引入了 record struct 以及推荐在高性能场景使用 struct 的原因。

💡面试延伸追问（预判面试官后续提问）

  1. String 是值类型还是引用类型？为什么它表现得像值类型？
    • 考点：string 是引用类型，但具有不可变性（Immutability）。每次修改字符串都会生成新对象，所以看起来像值拷贝。此外，字符串驻留池（Intern Pool）也是常考点。
  2. 什么是装箱（Boxing）和拆箱（Unboxing）？对性能有什么影响？
    • 考点：将值类型转换为 object 或接口类型时发生装箱（堆分配+拷贝）；反之则为拆箱。频繁装箱拆箱会导致 GC 压力和 CPU 开销，应尽量避免（如使用泛型集合 List<int> 而非 ArrayList）。
  3. Struct 和 Class 除了内存分布外，还有哪些主要区别？
    • 考点：Struct 不能有显式的无参构造函数，不能被继承，可以实现接口，支持析构函数吗？（不支持）。
  4. 在什么情况下应该使用 Struct 而不是 Class？
    • 考点：当数据结构简单、大小较小（建议小于 16 字节）、生命周期短、不需要继承、且需要高性能避免 GC 压力时。

五、什么是装箱（Boxing）和拆箱（Unboxing）

✅面试简答（考场口述答案）

装箱（Boxing）是将值类型转换为引用类型（object 或接口）的过程；拆箱（Unboxing）是将引用类型显式转换回值类型的过程。

  • 装箱：在堆上分配内存，将值类型的副本拷贝到堆中，并返回该对象的引用。
  • 拆箱：检查对象实例是否是给定的值类型，如果是，则将堆中的值拷贝回栈上的值类型变量。
  • 核心影响：两者都涉及内存分配和数据拷贝，频繁操作会增加 GC（垃圾回收） 压力并降低性能，应在高性能场景中尽量避免。

📚深入解析

1. 底层原理与内存变化

C# 的类型系统统一了所有类型（都继承自 System.Object），但值类型和引用类型的存储方式不同。为了让值类型能像引用类型一样被处理（例如存入 ArrayList 或传给接收 object 参数的方法），CLR 必须进行“包装”。

  • 装箱过程 (Boxing)：

    1. 在托管堆（Heap）中分配一个新的对象内存空间。
    2. 该空间包含两部分：类型对象指针、同步块索引（引用类型头信息）以及值类型的数据副本。
    3. 将栈上的值拷贝到堆中。
    4. 返回堆中对象的地址（引用）。

  • 拆箱过程 (Unboxing)：

    1. 检查对象实例是否确实是由该值类型装箱而来的（类型检查）。
    2. 获取堆中对象的值部分。
    3. 将值从堆拷贝回栈上的值类型变量中。

2. 代码示例 

int i = 123;

// 1. 装箱 (Boxing)
// 隐式转换：int -> object
// 发生：堆分配 + 内存拷贝
object o = i; 

// 2. 拆箱 (Unboxing)
// 显式转换：object -> int
// 发生：类型检查 + 内存拷贝
int j = (int)o;

3. 常见的隐性装箱陷阱

面试官通常更关注你是否有意识去避免隐性装箱，因为显式装箱很容易被发现。

场景 说明 优化方案
非泛型集合 ArrayList list = new ArrayList(); list.Add(10); Add 参数是 object，导致装箱。 使用泛型集合 List<int>
字符串拼接 string s = "Value: " + 10; 编译器通常会调用 ToString()，但如果手动调用 string.Format 或旧式拼接可能触发。 使用插值字符串 $"Value: {10}" 或 StringBuilder
虚方法调用 值类型调用继承自 System.ValueType 的虚方法（如 Equals, GetHashCode, ToString）时，如果未被重写，可能触发装箱。 为 struct 重写这些方法
接口转换 struct MyStruct : IMyInterface {} IMyInterface iface = myStruct; 将 struct 赋值给接口变量会触发装箱。 尽量让 struct 不实现接口，或在泛型约束中处理

4. 性能影响

  1. CPU 开销：内存拷贝和类型检查需要 CPU 周期。
  2. GC 压力：每次装箱都会在堆上产生一个临时对象。如果在一个循环中频繁装箱，会产生大量短期存活的对象，导致 Gen 0 GC 频繁触发，甚至引发暂停，严重影响吞吐量。

💡面试延伸追问（预判面试官后续提问）

  1. 如何检测代码中是否存在装箱操作？
    • 考点：使用 Visual Studio 的性能分析器（Performance Profiler）、ILSpy 查看生成的 IL 代码（查找 box 和 unbox 指令），或使用静态分析工具。
  2. 泛型（Generics）是如何解决装箱问题的？
    • 考点：泛型在 JIT 编译时会生成特定类型的代码（如 List<int> 直接存储 int 数组），避免了转换为 object，从而消除了装箱/拆箱开销。这是泛型相比 ArrayList 的核心优势之一。
  3. string 是引用类型，那 string 和 int 拼接时会发生装箱吗？
    • 考点：不会。编译器会将 int 转换为 string（调用 ToString()），然后进行引用类型的字符串拼接。虽然 ToString() 内部可能有逻辑，但这不属于“装箱”定义中的值转引用对象过程。
  4. 对于高性能要求的场景，除了使用泛型，还有什么手段避免装箱？
    • 考点：使用 Span<T>, Memory<T>，使用 ref struct，或者使用 IEquatable<T> 接口替代默认的 Equals(object) 以避免值类型比较时的装箱。

七、C# 中如何处理异常

✅面试简答（考场口述答案）

C# 使用 try-catch-finally 结构进行异常处理：

  1. try：包裹可能抛出异常的代码。
  2. catch：捕获并处理特定类型的异常，建议按从具体到通用的顺序排列。
  3. finally：无论是否发生异常都会执行，通常用于释放资源（如关闭连接、文件流）。
  4. throw：用于重新抛出异常。建议使用 throw; 保留原始堆栈信息，避免使用 throw ex; 重置堆栈。
  5. 最佳实践：只捕获你能够处理的异常，不要吞掉异常（空的 catch），在 ASP.NET Core 中通常结合全局中间件统一处理未捕获异常。

📚深入解析

1. 基本语法结构 

try
{
    // 可能出错的代码
    int result = 10 / 0;
}
catch (DivideByZeroException ex)
{
    // 捕获特定异常
    Console.WriteLine($"除数不能为零: {ex.Message}");
}
catch (Exception ex)
{
    // 捕获所有其他异常（必须放在最后）
    Console.WriteLine($"发生未知错误: {ex.Message}");
}
finally
{
    // 无论如何都会执行，用于清理资源
    Console.WriteLine("清理工作完成。");
}

2. throw vs throw ex （高频考点）

  • throw;：重新抛出当前捕获的异常。优点：保留原始的堆栈跟踪（Stack Trace），方便定位最初出错的位置。
  • throw ex;：抛出一个新的异常对象。缺点：堆栈跟踪会被重置，指向当前 catch 块的位置，丢失了原始出错点的信息，不利于调试。
catch (Exception ex)
{
    // 记录日志
    _logger.LogError(ex, "Error occurred");
    
    // ✅ 推荐：保留原始堆栈
    throw; 
    
    // ❌ 不推荐：重置堆栈
    // throw ex; 
}

3. 异常过滤器（Exception Filters - C# 6+）

可以在 catch 后面添加 when 子句，根据条件决定是否捕获异常。这比在 catch 块内部再写 if 判断更高效且逻辑更清晰。

try 
{
    // ...
}
catch (Exception ex) when (ex is IOException && IsNetworkError(ex))
{
    // 仅当是 IO 异常且为网络错误时捕获
    RetryOperation();
}

4. 资源管理：using 语句

对于实现了 IDisposable 接口的对象（如文件流、数据库连接），使用 using 可以确保即使发生异常，资源也能被正确释放。它本质上是 try-finally 的语法糖。

// C# 8.0+ using 声明
using var stream = new FileStream("test.txt", FileMode.Open);
// 代码块结束时自动调用 stream.Dispose()

5. ASP.NET Core 中的全局异常处理

在后端开发中，不建议在每个 Controller 方法里写 try-catch。通常采用以下策略：

  • 异常中间件（Exception Handling Middleware）：在 Program.cs 中配置，捕获所有未处理的异常，返回统一的 JSON 错误格式。
  • 过滤器（Filters）：实现 IExceptionFilter 接口。
  • Problem Details：遵循 RFC 7807 标准，提供标准化的错误响应。

💡面试延伸追问（预判面试官后续提问）

  1. 什么是异常的性能开销？为什么不能用异常来控制流程？
    • 考点：抛出异常时，CLR 需要暂停执行，搜索 catch 块，收集堆栈信息，这个过程非常昂贵（比布尔返回值慢几个数量级）。因此，应使用 int.TryParse 而非 try { int.Parse() } catch 来处理用户输入。
  2. Finalize（析构函数）和 Dispose 有什么区别？
    • 考点：Dispose 是确定性释放（手动或 using 调用），用于释放非托管资源；Finalize 是非确定性释放（由 GC 调用），性能开销大，应尽量避免依赖它。
  3. 如何设计一个自定义异常类？
    • 考点：继承自 Exception（或更具体的 ApplicationException 已废弃，直接继承 Exception），建议提供至少三个构造函数（无参、带消息、带消息和内层异常），并标记 [Serializable]。
  4. 在 async/await 异步方法中，异常是如何捕获的？
    • 考点：异步方法中的异常会被捕获并存储在返回的 Task 对象中。只有当你对 Task 进行 await 时，异常才会被重新抛出到当前的同步上下文。如果忘记 await，异常可能会被静默吞掉（取决于配置）。

八、C#中有哪些访问修饰符

✅面试简答（考场口述答案）

C# 主要有 5 种访问修饰符，用于控制类、方法、字段等成员的可访问性：

  1. public：公开。任何代码都可以访问，无限制。
  2. private：私有。只有同一个类或结构体内部可以访问。这是默认的类成员访问级别。
  3. protected：受保护。只有同一个类及其**派生类（子类）**可以访问。
  4. internal：内部。只有同一个程序集（Assembly，即 .dll 或 .exe）内的代码可以访问。这是默认的类访问级别。
  5. protected internal：受保护或内部。同一程序集内的任何代码，或者不同程序集中的派生类都可以访问。（注意是“或”的关系）。

补充：C# 7.2 引入了 private protected，仅限同一程序集内的派生类访问。

📚深入解析

1. 访问权限对比表

修饰符 同一类 同程序集 (Assembly) 派生类 (不同程序集) 任何代码
private ✅ ❌ ❌ ❌
internal ✅ ✅ ❌ ❌
protected ✅ ❌ ✅ ❌
protected internal ✅ ✅ ✅ ❌
private protected ✅ ❌ ✅ (仅同程序集) ❌
public ✅ ✅ ✅ ✅

2. 关键概念辨析

  • 默认访问级别：
    • 命名空间级别的**类（Class）**的默认级别是 internal，对于嵌套类的默认级别是private。如果你不写修饰符，其他项目（程序集）无法引用该类。
    • **类成员（字段、方法）**的默认级别是 private。这符合封装原则，防止外部随意修改内部状态。
  • protected internal 的逻辑：
    • 它是 protected OR internal。
    • 场景：你想让同一个库里的所有类都能用这个方法，同时也想让继承了这个库的其他项目里的子类也能重写或使用这个方法。
  • private protected 的逻辑：
    • 它是 private AND protected（且限制在同程序集）。
    • 场景：非常严格的限制，只允许“自家兄弟”（同程序集）里的“后代”（子类）访问。

3. 常见应用场景

  • public：API 接口、对外暴露的服务方法、DTO 模型。
  • private：内部辅助方法、私有字段（配合 Property 使用）。
  • internal：库内部的工具类、不希望被外部项目直接调用的实现细节。
  • protected：基类中希望子类重写的方法（如 virtual void Process()）或共享的状态。

4. 代码示例 

// Assembly A
public class BaseClass
{
    private int _id; // 仅 BaseClass 可用
    internal string Name { get; set; } // Assembly A 内可用
    protected int Age { get; set; } // BaseClass 及子类可用
    protected internal void Show() { } // Assembly A 内可用 OR 任何地方的子类可用
}

public class DerivedClass : BaseClass
{
    public void Test()
    {
        // _id = 1; // Error: private
        this.Name = "Test"; // OK: internal (同程序集)
        this.Age = 10; // OK: protected (子类)
        this.Show(); // OK: protected internal
    }
}

💡面试延伸追问（预判面试官后续提问）

  1. internal 和 public 在微服务或类库设计中如何选择？
    • 考点：最小权限原则。只暴露必要的 API 为 public，将内部实现细节标记为 internal，这样可以随时重构内部代码而不破坏外部依赖，提高库的稳定性。
  2. 什么是友元程序集（InternalsVisibleTo）？
    • 考点：如果希望另一个特定的程序集（如单元测试项目）能访问当前程序集的 internal 成员，可以在 AssemblyInfo.cs 或 .csproj 中使用 [assembly: InternalsVisibleTo("MyTestProject")]。这在编写单元测试时非常有用。
  3. 接口（Interface）中的成员可以有访问修饰符吗？
    • 考点：在 C# 8.0 之前，接口成员隐式为 public，不能加修饰符。C# 8.0 引入了默认接口实现，允许接口成员有实现体，但访问级别依然受到严格限制（通常仍视为公开契约的一部分，但可以有 private 辅助方法在接口内部复用）。
  4. 为什么字段通常设为 private，而通过 Property 暴露？
    • 考点：封装。Property 可以在 get/set 中加入逻辑验证、通知机制（如 INotifyPropertyChanged）或懒加载，而直接暴露 public 字段则失去了这些控制权。

九、sealed修饰符的作用是什么

✅面试简答（考场口述答案）

sealed 修饰符主要有两个作用：

  1. 密封类：当修饰类时，表示该类不能被继承。任何尝试继承该类的操作都会导致编译错误。
  2. 密封方法/属性：当修饰重写的方法或属性（override）时，表示该方法在派生类中不能再被进一步重写。

核心目的：限制继承层次，保护设计意图，防止子类破坏基类的逻辑完整性，同时在某些情况下能帮助 JIT 编译器进行性能优化（去虚拟化）。

📚深入解析

1. 密封类 (Sealed Class)

  • 语法：public sealed class MyClass { }
  • 特点：
    • 不能有子类。
    • 通常用于工具类、静态类（隐式密封）或为了安全/性能考虑不希望被扩展的类。
    • 经典案例：C# 中的 string 类就是 sealed 的。这是为了保证字符串的不可变性（Immutability）和安全性，防止有人通过继承篡改字符串的行为。

2. 密封成员 (Sealed Member)

  • 语法：必须与 override 连用，即 public sealed override void Method() { }
  • 场景：
    • 基类定义了一个虚方法 virtual。
    • 中间层子类重写了该方法 override，并认为自己的实现已经是最终版本，不希望后续的子类再修改这个逻辑。
    • 此时使用 sealed override 锁定该方法。
public class Base
{
    public virtual void DoWork() { Console.WriteLine("Base"); }
}

public class Middle : Base
{
    // 重写并密封，后续子类无法再重写 DoWork
    public sealed override void DoWork() { Console.WriteLine("Middle"); }
}

public class Derived : Middle
{
    // ❌ 编译错误：Cannot override inherited member 'Middle.DoWork()' because it is sealed
    // public override void DoWork() { } 
}

3. 性能优化（JIT 去虚拟化）

  • 原理：调用虚方法（Virtual Method）时，CLR 需要通过虚方法表（V-Table）查找实际要执行的方法地址，这比直接调用非虚方法稍慢。
  • 优化：如果一个类是 sealed 的，或者一个虚方法被 sealed 了，JIT 编译器在编译机器码时就能确定该方法不可能再有其他重写版本。因此，它可以直接调用该方法的具体实现，跳过 V-Table 查找过程。这种优化称为“去虚拟化”（De-virtualization）。
  • 注意：在现代 .NET (Core/5+) 中，JIT 非常智能，即使没有 sealed，它也能通过内联缓存（Inline Caching）等技术优化很多虚调用，但显式使用 sealed 依然是一个明确的性能提示。

4. 为什么 string 是 sealed 的？

  1. 安全性：字符串常用于存储敏感信息（如密码、SQL 连接串）。如果允许继承，恶意代码可能创建一个伪装成 string 的子类，篡改其行为。
  2. 不可变性：string 的核心契约是不可变。如果允许继承，子类可能会引入可变状态，破坏哈希码的一致性（Hash Code Consistency），导致在 Dictionary 或 HashSet 中出现严重 Bug。
  3. 字符串驻留池（Intern Pool）：CLR 内部对字符串有优化机制，密封类更容易被运行时特殊处理。

💡面试延伸追问（预判面试官后续提问）

  1. 抽象类（Abstract Class）可以是 sealed 的吗？
    • 考点：不可以。abstract 意味着必须被继承才能实现，而 sealed 意味着禁止继承，两者语义冲突。
  2. 结构体（Struct）可以是 sealed 的吗？
    • 考点：结构体隐式就是密封的。因为 struct 是值类型，不支持继承（只能实现接口），所以你不能给 struct 加 sealed 关键字，但它本质上具有 sealed 的特性。
  3. 在设计模式或框架开发中，什么时候应该主动使用 sealed？
    • 考点：当你设计一个类库，且确定某个类的逻辑是完整的、不需要也不希望用户通过继承来扩展时。例如：DTO 对象、实体类（Entity）、工具帮助类。这符合“组合优于继承”的原则，减少耦合。
  4. static 类和 sealed 类有什么区别？
    • 考点：static 类隐式是 sealed 且 abstract 的。它不能实例化，也不能被继承，所有成员必须是静态的。而普通的 sealed 类可以实例化，只是不能被继承。

十、params关键字的作用是什么

✅面试简答（考场口述答案）

params 关键字用于声明可变数量的参数。它允许调用者在调用方法时，传入任意数量（包括零个）的指定类型参数，而无需显式创建数组。

  • 底层实现：编译器在编译时会将这些分散的参数自动打包成一个数组传递给方法。
  • 限制：一个方法只能有一个 params 参数，且它必须是参数列表中的最后一个参数。
  • 常见场景：string.Format, Console.WriteLine, Path.Combine 等。

📚深入解析

1. 语法与使用示例 

public class MathHelper
{
    // 定义一个可以接收任意个数 int 的方法
    public static int Sum(params int[] numbers)
    {
        if (numbers == null || numbers.Length == 0) return 0;
        
        int total = 0;
        foreach (var num in numbers)
        {
            total += num;
        }
        return total;
    }
}

// 调用方式 1：直接传多个参数（语法糖，编译器会自动创建数组）
int result1 = MathHelper.Sum(1, 2, 3, 4, 5); 

// 调用方式 2：直接传数组（完全合法）
int[] arr = { 10, 20 };
int result2 = MathHelper.Sum(arr);

// 调用方式 3：不传参数（numbers 为一个长度为 0 的空数组，而非 null）
int result3 = MathHelper.Sum();

2. 编译原理（IL 层面）

当你写 Sum(1, 2, 3) 时，C# 编译器（Roslyn）会在生成的 IL（中间语言）中将其转换为：

  1. 创建一个 int[3] 数组。
  2. 将 1, 2, 3 填入数组。
  3. 调用 Sum(int[]) 方法。

这意味着：params 只是编译器的语法糖，运行时并没有特殊的“可变参数”机制，本质上还是数组传递。

3. 关键规则与陷阱

  • 位置限制：params 必须是最后一个参数。 
    // ✅ 正确
void Log(string level, params string[] messages) {}

// ❌ 错误：CS0231 A parameter array must be the last parameter in a formal parameter list
void Log(params string[] messages, string level) {}
  • 唯一性：一个方法签名中只能有一个 params 参数。
  • 优先级：如果存在重载方法，编译器会优先匹配非 params 的精确匹配版本。只有当没有精确匹配时，才会考虑 params 版本。 
    void Print(string s) { ... }       // 优先匹配这个
void Print(params string[] args) { ... } 

Print("Hello"); // 调用第一个
Print("Hello", "World"); // 调用第二个
  • 空调用行为：如果调用时不给 params 传任何值（如 Sum()），方法内部接收到的数组是一个长度为 0 的空数组 (new int[0])，而不是 null。因此通常不需要判空，但判长是好的习惯。

4. 性能考量

由于每次调用 params 方法（除非直接传已有数组）都会在堆上分配一个新的数组对象：

  • 高频调用场景：如果在紧密循环中频繁调用带 params 的方法，会产生大量的短期数组对象，增加 GC（垃圾回收） 压力。
  • 优化建议：在高性能敏感代码中，可以考虑提供接受 Span<T> 或 ArraySegment<T> 的重载，或者直接使用数组/集合作为参数，避免隐式分配。

💡面试延伸追问（预判面试官后续提问）

  1. params object[] 有什么特殊之处？为什么不建议在高性能场景使用？
    • 考点：params object[] 会导致严重的**装箱（Boxing）**问题。如果你传 Sum(1, 2)，每个 int 都会被装箱成 object，产生额外的堆分配和拷贝开销。这是 .NET 早期 API 设计的历史遗留问题，现代 API 倾向于使用泛型或 Span<T>。
  2. 如果我想设计一个方法，既支持单个元素，又支持多个元素，该如何设计重载？
    • 考点：考察重载解析优先级。通常提供一个单参数方法和一个 params 数组方法。编译器会根据参数数量自动选择最匹配的重载。
  3. C# 12 引入了 params Span<T> 和 params ReadOnlySpan<T>，这解决了什么问题？
    • 考点：这是最新的性能优化特性。允许调用者传入栈分配的 stackalloc 数组或切片，完全避免了堆内存分配（Zero-allocation），极大地提升了高性能场景下的表现。
  4. params 参数可以是 null 吗？
    • 考点：如果你显式传递 null（如 Sum(null)），那么方法内部接收到的就是 null，而不是空数组。这会引发 NullReferenceException。所以最佳实践是在方法内部同时检查 null 和 Length。
