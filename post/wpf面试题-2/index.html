C# WinForm 和 WPF 中级面试题整理

1、是否使用过委托，一般在何时使用委托

委托传递的参数是一个方法，委托是给调用者使用的，在调用者不知道什么时候会使用的情况会使用委托，所以调用者需要提前订阅它然后执行自己的代码，当委托对象有了订阅者的触发消息后就会通知调用者。

【补充】

  • 委托（delegate）是引用类型，本质是对"方法"的抽象，可以把方法当作参数传递、当作变量保存，再在合适的时机调用（回调）。
  • 典型使用场景：
    • 事件与回调（如按钮点击、串口数据到达时通知 UI）；
    • 跨线程更新 UI（Dispatcher.Invoke / BeginInvoke 传入委托）；
    • 通用算法（如 List<T>.Sort(Comparison<T>)、Array.FindAll(Predicate<T>)）。
  • 基础示例：
// 1. 声明委托类型
public delegate void MyDelegate(string msg);

// 2. 实例化（指向一个方法）并调用
MyDelegate d = Console.WriteLine;
d("hello"); // 输出 hello
  • 现代开发中，Action<T> / Func<T> 等泛型委托可以免去显式声明委托类型。

2、是否使用过匿名委托及 Lambda 表达式

采用匿名方法实例化的委托称为匿名委托。Lambda 表达式本质上是改进的匿名委托。

【补充】

  • 匿名委托：用 delegate 关键字内联定义方法体，不单独命名方法：
MyDelegate d = delegate (string msg) { Console.WriteLine(msg); };
  • Lambda 表达式更简洁，是匿名方法的"语法糖"：
MyDelegate d = msg => Console.WriteLine(msg);
// 多个参数： (a, b) => a + b
// 有返回值：  (x) => x * 2
  • 应用：配合 LINQ 的 Where、Select、OrderBy 等使用；在事件订阅中代替显式方法。

3、是否使用过多线程，何时使用多线程，使用多线程应注意什么

需要注意的点：

  1. 子线程不可直接调用主线程的 UI 对象，可以调用主线程自定义的对象；
  2. 多线程同时访问一个资源时，要注意同步问题，对于同一个资源，可进行加锁操作。

线程同步的三种方式：阻塞（sleep() 或者 join()）；加互斥锁（lock）；使用信号量控制（AutoResetEvent 和 ManualResetEvent 初始化信号量，调用 set() 或者 reset() 方法改变信号量状态，调用 waitOne() 让线程继续）。

【补充】

  • 使用场景：耗时计算（避免 UI 卡顿）、IO 操作（文件/网络/串口读写）、并行处理大批量数据、定时任务。
  • WPF 中子线程更新 UI 的正确姿势：通过 Dispatcher 封送（this.Dispatcher.Invoke(...)），或者通过数据绑定 + INotifyPropertyChanged 让框架自动同步，而不是直接操作控件。
  • 同步机制扩展：lock（本质是 Monitor）、Monitor、Mutex、Semaphore/SemaphoreSlim、Interlocked（原子操作）、volatile（可见性）、Task + async/await（推荐）。
  • 注意事项：
    • lock 的锁对象必须是引用类型（值类型每次装箱产生新对象，锁会失效）；
    • 避免死锁：多个锁的获取顺序保持一致、避免在持锁期间调用可能阻塞的外部方法；
    • 优先使用 Task / async-await 而不是裸 Thread：线程池复用、支持返回值、支持取消（CancellationToken）。
  • 原文中的 john() 应为 join()（等待线程结束）；Thread.Sleep 是让出 CPU 指定时长。

4、异步

在处理一些长线的调用时，经常会导致界面停止响应，这个时候我们就需要使用异步编程，不需要等待响应，尽快的返回请求。C# 中一般使用 BeginInvoke 和 EndInvoke 用来执行异步操作。Async/Await 语法糖的理解。

【补充】

  • BeginInvoke/EndInvoke（APM 异步编程模型）是 .NET 早期的异步方式，现已基本被 TAP（基于 Task 的异步模式） 取代，面试中重点掌握 async/await 即可。
  • async/await 的本质：编译器会把 async 方法改造成一个状态机；遇到 await 时方法挂起并立即返回，不阻塞调用线程，异步操作完成后从挂起点继续执行。因此 UI 线程不会被阻塞。
  • 关键点：
    • await 后默认会回到调用上下文（WPF 中即 UI 线程），所以 await 之后可以直接安全地更新控件；
    • 返回值：有结果用 Task<T>，无结果用 Task；void 只用于事件处理器（async void 异常无法被捕获，尽量避免）；
    • 在类库代码中常用 ConfigureAwait(false) 避免捕获 UI 上下文，提升性能；
    • 可用 Task.Run(() => ...) 把 CPU 密集操作丢到线程池。
  • 简单示例：
private async Task<string> LoadDataAsync()
{
    // 模拟耗时IO，不阻塞UI线程
    string result = await Task.Run(() => FetchFromDevice());
    return result;
}

5、是否使用过反射，使用场景和目的

在分离式插件模式中使用反射。一般在系统搭建好后，通过在配置文件中新增插件信息，程序会自动加载插件。这样不用修改程序。

【补充】

  • 反射（Reflection）指在运行时动态获取程序集、类型、成员的元数据，并可动态创建实例、调用方法、读写属性。
  • 核心入口：Type 对象（通过 typeof(T)、obj.GetType() 或 Type.GetType("全名") 获得）。
  • 常见场景：
    • 插件化架构：扫描程序集并按约定动态加载（如 Activator.CreateInstance）；
    • ORM / 序列化框架内部（EF Core、Json.NET 等底层都依赖反射）；
    • 属性（Attribute）驱动的功能（如 MVC 路由、数据校验）；
    • 单元测试中调用私有方法。
  • 注意：反射有性能开销和类型安全问题，高频路径应避免（可配合表达式树/缓存优化）。

6、是否使用过泛型及泛型约束，使用场景

当用一个方法来处理传入不同种类型参数的时候需要使用泛型。泛型约束为了解决泛型不安全的问题。在实际情况中，约束的类型 T，使 T 遵循一定规则，必须继承某个类，或者必须实现某个接口，用 where 来实现。

Demo：实现一个基类约束。

public static void Show<T>(T tParameter) where T : People
{
    Console.WriteLine($"{tParameter.Id}_{tParameter.Name}");
    tParameter.Hi();
}

【补充】

  • 泛型优点：类型安全（编译期检查）、代码复用（一套代码多种类型）、性能（值类型免装箱）、扩展性好。
  • 常见约束组合（用 where T : ... 声明）：
约束写法 含义
where T : class T 必须是引用类型
where T : struct T 必须是值类型
where T : new() T 必须有公共无参构造函数（须放在约束列表最后）
where T : 基类名 T 必须继承自指定基类（可为派生类）
where T : 接口名 T 必须实现指定接口
where T : notnull T 不允许为 null（C# 8+）
where T : U T 必须是 U 或 U 的派生类
  • 一个类型参数可以有多个约束：where T : People, IComparable<T>, new()。

7、是否使用 LINQ，使用场景

在查询数据库时，不用调用特殊的数据库语法，可以直接编译查询语句。

【补充】

  • LINQ（Language Integrated Query，语言集成查询）：把查询能力内建到 C# 语言中，可统一查询内存集合（LINQ to Objects）、数据库（LINQ to SQL / EF）、XML（LINQ to XML）等数据源。
  • 常用操作符：Where（过滤）、Select（投影）、OrderBy/OrderByDescending（排序）、GroupBy（分组）、Join（连接）、Any/All（判断）、First/FirstOrDefault、Sum/Count/Average、Distinct、Skip/Take（分页）。
  • 两种语法：方法语法 list.Where(x => x.Age > 18)；查询语法 from x in list where x.Age > 18 select x。
  • 关键特性：延迟执行（deferred execution）——只有遍历（或调用 ToList() 等）时才真正执行；链式调用中注意一次遍历只取所需列。
var adults = persons.Where(p => p.Age >= 18)
                    .OrderBy(p => p.Name)
                    .Select(p => new { p.Name, p.Age })
                    .ToList();

8、单例模式

单例模式的基本样式。饿汉和懒汉的类型。

【补充】

  • 单例模式：保证一个类在整个进程中只有一个实例，并提供全局访问点。常用于配置文件管理、日志、数据库连接池等。
  • 饿汉式：类加载时即创建实例（静态字段初始化），由 CLR 保证线程安全，缺点是可能提前占用资源：
public sealed class Singleton
{
    private static readonly Singleton _instance = new Singleton();
    public static Singleton Instance => _instance;
    private Singleton() { }
}
  • 懒汉式：首次访问时才创建。线程安全的推荐写法（Lazy<T> 默认线程安全）：
public sealed class Singleton
{
    private static readonly Lazy<Singleton> _instance =
        new Lazy<Singleton>(() => new Singleton());
    public static Singleton Instance => _instance.Value;
    private Singleton() { }
}
  • 经典双检锁（Double-Checked Locking）写法也常考，要点：私有构造函数 + 静态字段 + lock + 双重 if (instance == null) 判断。

9、如何理解面向对象，自己的程序设计是否坚持面向对象设计

面向对象能够提供给我的是一种编程思想，在做任何软件之前会先将事务逻辑抽象化，从属性、方法、接口、继承几方面来解决问题。并不是所有的程序都需要面向对象，在一些小程序中，有些时候就没有必要面向对象，一个类能解决问题就用一个类解决，过度的封装和抽象也会造成代码可读性下降，以及运行效率的下降。如果面对的是复杂关系的需求，就应该尽可能将有关联的行为抽象成类。我的基本原则就是在能将事物抽象化的需求中使用面向对象。

【补充】

  • 三大特征：封装（数据+行为捆绑，隐藏内部细节）、继承（代码复用、is-a 关系）、多态（同一接口不同实现，运行时行为不同）。
  • 面向对象设计原则（SOLID）：
    • 单一职责（SRP）：一个类只做一件事；
    • 开闭原则（OCP）：对扩展开放、对修改关闭；
    • 里氏替换（LSP）：派生类可替换基类而不破坏程序；
    • 接口隔离（ISP）：接口尽量小而专；
    • 依赖倒置（DIP）：依赖抽象，不依赖具体实现。
  • 原文观点合理：小型/一次性脚本不必强行 OOP，过度设计同样是坏味道。

10、如何理解"三层"，自己的设计是否基于三层

三层基本划分为 UI、BLL、DAL。三层之间为单项传递，UI 负责界面与用户的交互，BLL 负责业务逻辑处理，DAL 负责与数据库的交互。三层的存在的目的是为了解耦。就是软件设计中说的"高内聚，低耦合"。一般在使用过程中会加入 Entity 层用于三层数据的交互。

【补充】

  • 标准分层：
    • UI（表现层）：界面展示与用户输入，不做业务逻辑；
    • BLL（业务逻辑层）：核心业务规则、流程编排；
    • DAL（数据访问层）：负责与数据库交互（增删改查）；
    • 附加：Entity/Model 层（实体模型，跨层传递数据）、Common 层（公共工具）。
  • 依赖方向：UI → BLL → DAL，上层依赖下层接口，下层不反向依赖上层。
  • 优点：职责清晰、便于分工、可独立测试、替换数据库时只改 DAL。
  • 现代架构演进：三层思想仍是基础，实际工程中常与 DDD（领域驱动设计）、MVVM、依赖注入等结合。

11、如何理解控制反转，是否使用过依赖注入，是否有自己的封装

IOC（Inversion of Control，控制反转）；DI（Dependence Injection，依赖注入）。

【补充】

  • 控制反转（IoC）：对象不再自己 new 依赖对象，而是把创建和注入的主动权反转给外部容器（IoC 容器），从而降低类之间的耦合。
  • **依赖注入（DI）**是实现 IoC 的最常见方式，有三种注入形式：
    • 构造函数注入（最推荐，依赖清晰、便于测试）；
    • 属性注入；
    • 方法注入。
  • 示例：接口 + 构造函数注入
public interface ILogger { void Log(string msg); }
public class FileLogger : ILogger { public void Log(string msg) { /* ... */ } }

public class OrderService
{
    private readonly ILogger _logger;
    public OrderService(ILogger logger)  // 依赖由外部注入，而不是自己 new
    {
        _logger = logger;
    }
}
  • 常用容器：Microsoft.Extensions.DependencyInjection（.NET 内置）、Autofac、Unity。
  • 好处：解耦、可测试性（注入 mock）、灵活替换实现、便于统一管理生命周期。

12、Ado.net 2.0，简单介绍 Ado.net 2.0 的常用类或对象，是否使用 Ado.net 2.0 封装过自己的数据层

Connection：打开数据库连接。

Command：执行数据库命令。

DataAdapter：连接数据。

DataSet：获取数据的缓存。

DataReader：只读数据库。

【补充】

  • 五大核心对象及职责：
对象 职责
Connection 建立与数据库的连接（Open() / Close()）
Command 执行 SQL 语句/存储过程（ExecuteNonQuery / ExecuteReader / ExecuteScalar）
DataReader 只进只读的流式读取，占用资源小、速度快，读取时需保持连接打开
DataAdapter 桥梁：把查询结果填充进 DataSet（Fill），也可把改动更新回数据库（Update）
DataSet 内存中的"小数据库"，可离线使用（断开连接后仍可操作）
  • 配合使用 using 语句及时释放连接；ConnectionString 中的连接池（Pooling）默认开启。
  • 示例（经典 ADO.NET 查询）：
using (var conn = new SqlConnection(connStr))
{
    conn.Open();
    using (var cmd = new SqlCommand("SELECT * FROM Users WHERE Id=@id", conn))
    {
        cmd.Parameters.AddWithValue("@id", 1); // 参数化，防SQL注入
        using (var reader = cmd.ExecuteReader())
        {
            while (reader.Read()) { /* 处理行 */ }
        }
    }
}
  • 实际项目更常用 EF Core / Dapper 等 ORM，但 ADO.NET 作为底层基础仍是高频考点。

13、序列化与反序列化的数据转换，如 Json、Xml、DataTable、泛型之间的转换，做过哪些，需要用哪些技术手段。是否做过这些转换的工具类

C# 中使用 Serialize 和 Deserialize 进行序列化和反序列化。

【补充】

  • JSON（最常用）：
// System.Text.Json（.NET Core 3.0+ 内置）
string json = JsonSerializer.Serialize(obj);
var obj = JsonSerializer.Deserialize<MyClass>(json);

// Newtonsoft.Json（第三方，功能更全）
string json = JsonConvert.SerializeObject(obj);
var obj = JsonConvert.DeserializeObject<MyClass>(json);
  • XML：使用 XmlSerializer（要求类型有公共无参构造函数）：
var xs = new XmlSerializer(typeof(MyClass));
using (var sw = new StringWriter()) { xs.Serialize(sw, obj); string xml = sw.ToString(); }
  • DataTable ↔ 泛型集合：DataTable 转 List<T> 常用反射逐行映射；List<T> 转 DataTable 同样反射生成列。也可借助第三方库（如 AutoMapper、FastDataTableConverter）。
  • 用途：网络传输（WebAPI 报文）、配置文件、缓存存储、对象深拷贝。
  • 工程上建议把常用转换封装成泛型工具类（如 JsonHelper.Serialize<T>），统一配置（忽略循环引用、时间格式、驼峰命名等）。

14、对内存数据库和数据仓储及持久化有多少了解

内存数据库是指把数据库放在内存中，磁盘作为 log 或者 checkpoint 备份。Checkpoint 是周期性的把内存数据中的数据同步到磁盘中。Log 是每次操作内存数据库之前，都生成一个 log，记录了对数据的修改操作，然后刷出标致，如果内存数据中的事物失败，就可以通过 log 回滚。如果操作准确，就根据 log 记录同步到磁盘数据库。

【补充】

  • 原文描述的是内存数据库的持久化机制（类似 Redis 的 RDB + AOF 思路）：
    • Checkpoint（快照/RDB）：周期性把内存数据整体落盘；
    • Log（日志/AOF）：每次写操作先记日志，崩溃/失败时通过日志恢复或回滚。
  • 内存数据库（Redis、Memcached 等）：数据主要在内存中，读写极快，用于缓存、会话、排行榜等。
  • 数据仓储（Repository）：数据访问层的一种设计模式，把数据读写封装成仓储接口（如 IRepository<T>），屏蔽底层数据库实现，便于测试和替换。
  • 持久化（Persistence）：把易失内存中的数据保存到磁盘/数据库，保证程序重启后数据不丢失。

15、托管代码和非托管代码的区别

区别：

  1. 托管代码是一种中间语言，运行在 CLR 上；非托管代码被编译为机器码，运行在机器上。
  2. 托管代码独立于平台和语言，能更好的实现不同语言平台之间的兼容；非托管代码依赖于平台和语言。
  3. 托管代码可享受 CLR 提供的服务（如安全检测、垃圾回收等），不需要自己完成这些操作；非托管代码需要自己提供安全检测、垃圾回收等操作。

【补充】

  • 托管代码（Managed Code）：C#/VB.NET 等编译为 IL（中间语言），由 CLR 负责 JIT 编译、GC 回收、类型安全检查和异常处理。
  • 非托管代码（Unmanaged Code）：C/C++ 等直接编译为机器码，自行管理内存，如 Win32 API、COM 组件、P/Invoke 调用的原生库。
  • C# 中通过 DllImport（P/Invoke）或 C++/CLI 与原生代码互操作。

16、托管资源和非托管资源

在 C/C++ 中，资源都是需要手动释放的，比如你 new 了一个指针，用过之后就需要 delete 掉，否则就会造成内存泄露。而在 Java 中，不必考虑资源释放的问题，Java 的垃圾回收机制（GC，Garbage Collection）会保证失效的资源被自动释放。

而 C# 的机制与 Java 类似，运行于 .net 平台上的代码，分配的资源一般会自动由平台的垃圾回收器释放，这样的资源就是托管资源。

但是一些例外的资源，如 System.IO.StreamReader 等各种流、各种连接所分配的资源，需要显式调用 Close() 或 Dispose() 释放，这种资源就叫做非托管资源。

【补充】

  • 托管资源：由 GC 自动管理（普通对象、字符串、数组等），无需手动释放。
  • 非托管资源：文件流、网络连接、数据库连接、GDI+ 句柄、互操作指针等，GC 无法自动回收，必须显式释放。
  • 正确释放方式：实现 IDisposable，用 using 语句确保释放：
using (var fs = new FileStream("a.txt", FileMode.Open))
{
    // 使用后自动调用 Dispose()
}
  • 若一个类持有非托管资源，应实现 IDisposable（并提供终结器 ~Class() 作为兜底，配合 GC.SuppressFinalize 避免重复回收）。

17、WPF 和 mvvm 的理解

WPF：Windows Presentation Foundation

MVVM 是 Model-View-ViewModel 的简写。在技术层面，WPF 也带来了诸如 Binding、Dependency Property、Routed Events、Command、DataTemplate、ControlTemplate 等新特性。

Model 里面定义方法和属性；ViewModel 里面定义 Binding 和 Command；View 里面定义 UI 控件。

【补充】

  • WPF：微软的桌面 UI 框架，核心特色：XAML 声明式 UI、数据绑定、依赖属性、路由事件、命令、模板（ControlTemplate/DataTemplate）、样式（Style）、动画、硬件加速渲染。非常适合工控/上位机等富客户端开发。
  • MVVM 三要素：

    • View：XAML 界面，只负责展示与交互；
    • ViewModel：桥接层，暴露可绑定属性与命令（ICommand），实现 INotifyPropertyChanged 通知属性变更。

18、SQL 和存储过程，为什么要用存储过程

存储过程（Stored Procedure）是在大型数据库系统中，一组为了完成特定功能的 SQL 语句集，存储在数据库中，经过第一次编译后再次调用不需要再次编译，用户通过指定存储过程的名字并给出参数（如果该存储过程带有参数）来执行它，存储过程是数据库中的一个重要对象；存储过程中可以包含逻辑控制语句和数据操纵语句，它可以接受参数、输出参数、返回单个或多个结果集以及返回值。

优点：

  • 由于应用程序随着时间推移会不断更改、增删功能，SQL 语句会变得更复杂，存储过程为封装此类代码提供了一个替换位置；
  • 由于存储过程在创建时即在数据库服务器上进行了编译并存储在数据库中，所以存储过程运行要比单个的 SQL 语句块要快；
  • 由于在调用时只需提供存储过程名和必要的参数信息，所以在一定程度上也可以减少网络流量，减轻网络负担；
  • 可维护性高，更新存储过程通常比更改、测试以及重新部署程序集需要较少的时间和精力；
  • 代码精简一致，一个存储过程可以用于应用程序代码的不同位置；
  • 增强安全性：通过向用户授予对存储过程（而不是基于表）的访问权限，它们可以提供对特定数据的访问；提高代码安全，防止 SQL 注入（但未彻底解决，例如将数据操作语言 DML 附加到输入参数）；SQLParameter 类指定存储过程参数的数据类型，作为深层次防御性策略的一部分，可以验证用户提供的值类型（但也不是万无一失，还是应该在传递至数据库前得到附加验证）。

缺点：

  • 如果更改范围大到需要对输入存储过程的参数进行更改，或者要更改由其返回的数据，则仍需要更新程序集中的代码以添加参数，等等；
  • 可移植性差，由于存储过程将应用程序绑定到 Server，因此使用存储过程封装业务逻辑将限制应用程序的可移植性；如果应用程序的可移植性在您的环境中非常重要，则将业务逻辑封装在不特定于 RDBMS 的中间层中可能是一个更佳的选择。

【补充】

  • 执行存储过程的 ADO.NET 写法：
using (var cmd = new SqlCommand("GetEmployeesByDepartment", conn))
{
    cmd.CommandType = CommandType.StoredProcedure;
    cmd.Parameters.AddWithValue("@DepartmentID", 1);
    // ...
}
  • 现代实践观点：存储过程适合复杂、稳定的数据操作逻辑（报表、批量处理、跨表事务）；但若业务逻辑变化频繁、需要跨数据库移植，则建议把逻辑放应用层，配合 ORM 管理。面试时能说出优缺点与适用场景即可。

19、反射

C# 中的反射常用于在程序的运行时获取类型的元数据，可获取的信息包括已加载到进程中的程序集和类型信息，它和 C++ 中的 RTTI（Runtime Type Information）的作用是差不多的。

为了能够使用反射，需要在项目中引用 System.Reflection 命名空间，在使用反射的开始，你会获取一个 Type 类型的对象，从这个对象上进一步获取程序集、类型、模块等信息，可以通过反射动态的生成某个类型的实例，甚至还能动态调用这个类型上的方法。

在 System.Reflection 命名空间下，定义了如下几大核心类型：Assembly、Module、Enum、MethodInfo、ConstructorInfo、MemberInfo、ParameterInfo、Type、FieldInfo、EventInfo、PropertyInfo。

【补充】

  • 简单使用示例：
Type t = typeof(MyClass);
// 动态创建实例
object obj = Activator.CreateInstance(t);
// 动态调用方法
MethodInfo mi = t.GetMethod("Hello");
mi.Invoke(obj, null);
  • 反射的常见应用见第 5 题补充；注意性能（可缓存 MethodInfo/PropertyInfo）与安全（Type.GetType 传入外部字符串需校验）。

20、流处理

FileStream 文件流；StreamReader StreamWriter 字节流（FileStream）；BinaryReader BinaryWriter 二进制流。

【补充】

  • 原文表述略有混淆，纠正如下：
    • FileStream：文件字节流，读写文件底层字节；
    • StreamReader / StreamWriter：文本流（按字符读写文本文件），内部可包一个 FileStream；
    • BinaryReader / BinaryWriter：二进制流（按基础类型读写二进制数据）；
    • 另有：MemoryStream（内存流）、BufferedStream（缓冲流）、NetworkStream（网络流）、GZipStream（压缩流）。
  • 示例（文本读写）：
// 写
using (var sw = new StreamWriter("log.txt", append: true)) { sw.WriteLine("hello"); }
// 读
using (var sr = new StreamReader("log.txt")) { string line = sr.ReadLine(); }
  • 所有流都建议用 using 管理释放；Stream.CopyTo 可方便地在流之间复制数据。

21、单元测试，private 能否做单元测试，范围

Right：验证结果（主要功能和逻辑）是否正确；

B：边界条件是否正确；

I：是否可以检查反向关联；这里所谓反向关联，是指用反向逻辑来验证我们的结果，比如说要验证平方根是否正确时，可以求这个平方根的平方跟我们的输入是否一致。

C：是否可以采用其他方法来 cross-check 结果；cross-check 是在单元测试中采用与实际模块中不同的方法来实现同样的功能作为期望结果，去与实际模块中得到的结果做对比。

E：错误条件是否可以重现；

P：性能方面是否满足条件。

【补充】

  • 上述是 RIGHT-BICEP 测试设计原则（出自《Pragmatic Unit Testing》）：Right（正确性）、Boundary（边界）、Inverse（反向验证）、Cross-check（交叉验证）、Error（错误路径）、Performance（性能）。
  • private 方法能否测试？ 可以，常用三种手段：
    1. 反射调用（typeof(Class).GetMethod("Method", BindingFlags.NonPublic | BindingFlags.Instance)）；
    2. 程序集特性 [assembly: InternalsVisibleTo("测试程序集名")]，把方法改为 internal；
    3. 更推荐的做法：重构——把私有逻辑提取到独立类或 internal 方法，通过公共 API 间接覆盖（私有细节不应成为测试契约）。
  • C# 常用测试框架：NUnit、xUnit、MSTest；Mock 框架：Moq、NSubstitute、FakeItEasy。
  • 断言风格：AAA（Arrange-Act-Assert）三段式组织用例。

22、C# 的修饰符

类的访问修饰符主要有两个，即 internal 和 public，如果省略了访问修饰符，即为 internal。

类中成员的访问修饰符有 4 个，具体用法如下：

  1. public：成员可以被任何代码访问。
  2. private：成员仅能被同一个类中的代码访问，如果在类成员前未使用任何访问修饰符，则默认为 private。
  3. internal：成员仅能被同一个项目（程序集）中的代码访问。
  4. protected：成员只能由类或派生类中的代码访问。

【补充】

  • 组合修饰符：
    • protected internal：同一程序集内任意代码 或 派生类可访问（并集）；
    • private protected（C# 7.2+）：同一程序集内的派生类可访问（交集）；
    • sealed（类不可继承）、static（静态成员）、abstract（抽象成员/类）、virtual/override（虚方法/重写）、readonly、const。
  • 修饰符也可修饰方法/属性/字段/事件，访问级别取决于"成员可见性 + 类型可见性"的较小者。

22（原文编号重复）、WCF 通信中的 ABC 基本概念

Address：每一个 WCF 的 Service 都有一个唯一的地址。这个地址给出了 Service 的地址和传输协议（Transport Protocol）。

Binding：通信（Communication）的方式很多，同步的 request/reply 模式，非同步的 fire-and-forget 模式。消息可以单向或者双向的发送接收，可以立即发送或者把它放入到某一个队列中再处理。所供选择的传输协议也有 Http、Tcp、P2P、IPC 等。当要考虑 Client/Server 如何进行通讯的时候，除了考虑以上提到的几点之外，还有其它很多需要考虑的因素，如安全、性能等。因此，简单来说，Binding 只不过是微软提供的一组考虑比较周全、常用的封装好的通信方式。

Contract：Contract 描述了 Service 能提供的各种服务。

  • [ServiceContract]：指明该接口是一个 WCF 的服务契约，可以被外部调用，不加则无法被外部调用。
  • [OperationContract]：指明该方法是一个 WCF 的方法契约，可以被外部调用，不加则无法被外部调用。
  • [DataContract]：数据契约，指明该类是可供服务端和客户端相互传递自定义数据的类型，声明后该类型就可以被序列化在服务端和客户端之间传送。
  • [DataMember]：数据成员，声明后的属性可以参与到客户端和服务器端的类的属性的序列化，没有声明的不参与序列化。

【补充】

  • WCF（Windows Communication Foundation）的 ABC 即：Address（服务地址，含传输协议）、Binding（通信方式/协议绑定，如 basicHttpBinding、netTcpBinding）、Contract（服务契约/数据契约/消息契约）。
  • 说明：WCF 在 .NET Core/.NET 5+ 中已不再默认提供（微软建议改用 gRPC、ASP.NET Core WebAPI），面试了解概念即可，不必深究实现。

24、string 和 stringbuilder 的区别

  1. string 继承 object 类，stringbuilder 继承 AbstractStringBuilder；
  2. string 是不可变类，stringbuilder 是可变类；
  3. stringbuilder 运行速度比 string 快。

【补充】（重要修正）

  • string 不可变：任何修改操作（+、Substring、Replace）都会创建新字符串对象，旧对象等待 GC。少量拼接（编译期常量）编译器会优化为 string.Concat，性能尚可。
  • StringBuilder 可变：内部维护字符数组，Append 等在原对象上修改，适合循环内大量拼接，避免频繁创建对象。
  • 正确结论：
    • 少量/固定次数拼接 → 用 string（简洁）；
    • 循环内大量拼接 → 用 StringBuilder（更快、省内存）。
  • 补充：string 是引用类型但表现像值类型（相等性比较的是内容）；== 对 string 比较的是值。
// 大量拼接场景：StringBuilder 明显更快
var sb = new StringBuilder();
for (int i = 0; i < 10000; i++) sb.Append(i).Append(',');
string result = sb.ToString();

25、属性变更通知（INotifyPropertyChanged 和 ObservableCollection<T>）

  1. INotifyPropertyChanged 向客户端发出某一属性值更改的通知。
  2. ObservableCollection<T> 类，它是实现 INotifyCollectionChanged 接口的数据集合的内置实现。表示一个动态数据集合，在添加项、移除项或刷新整个列表时，此集合将提供通知。

【补充】

  • 二者是 WPF/MVVM 数据绑定自动刷新的基础：
public class Person : INotifyPropertyChanged
{
    private string _name;
    public string Name
    {
        get => _name;
        set { _name = value; OnPropertyChanged(nameof(Name)); }
    }

    public event PropertyChangedEventHandler PropertyChanged;
    private void OnPropertyChanged(string propName) =>
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(propName));
}
  • ObservableCollection<T>：绑定到 ListBox/DataGrid 等后，Add/Remove/Clear 会自动刷新 UI；若修改某个元素的属性，仍需该元素实现 INotifyPropertyChanged。
  • 注意：List<T> 没有变更通知，改集合后 UI 不会自动更新，这是两者选择的依据。
  • 现代简化：可使用 CommunityToolkit.Mvvm 的 [ObservableProperty] 源生成器，避免手写样板代码。

26、什么是 XML 扩展 XAML？有何优点？

  1. XAML 是 eXtensible Application Markup Language 的英文缩写，相应于中文称为可扩展应用程序标记语言，它是微软公司为构建应用程序用户界面而创建的一种新的描述性语言。
  2. XAML 是 XML 语言的一个衍生物，它的语法与 XML 语言完全一致，它的功能就是专门用来设计和实现程序的 UI。
  3. XAML 一个很大的优点就是由于 WPF 支持 WEB 开发，那么 WEB 开发和桌面开发的转换是很简单，修改的地方很短，同时 UI 与逻辑完全分离，所以逻辑代码也几乎不用改动。

【补充】

  • XAML 与代码分离：.xaml 描述界面 + .xaml.cs 承载逻辑（code-behind），编译时自动生成 partial 类。
  • 主要优点：
    • 声明式 UI：界面即文档，易于阅读和维护；
    • UI 与逻辑分离：设计人员可独立调整界面；
    • 数据绑定/模板/样式/动画等特性与 XAML 深度集成；
    • 跨技术生态（WPF / UWP / WinUI / MAUI 都基于 XAML 思想），学习一次多处复用。

27、解释什么是依赖属性，它和以前的属性有什么不同？为什么在 WPF 会使用它？

  1. Windows Presentation Foundation (WPF) 提供了一组服务，这些服务可用于扩展公共语言运行时 (CLR) 属性的功能，这些服务通常统称为 WPF 属性系统。由 WPF 属性系统支持的属性称为依赖项属性。

  2. 它和以往属性的不同之处：

    （1）依赖属性是一种特定类型的属性。这种属性的特殊之处在于，其属性值受到 Windows 运行时中专用属性系统的跟踪和影响。

    （2）依赖属性的用途是提供一种系统的方式，用来基于其他输入（在应用运行时其内部出现的其他属性、事件和状态）计算属性的值。

    （3）依赖属性代表或支持编程模型的某种特定功能，用于定义 Windows 运行时应用，这种模型使用 XAML 编写 UI，使用 C#、Microsoft Visual Basic 或 Visual C++ 组件扩展（C++/CX）编写代码。

    一般的属性没有这么复杂。

  3. WPF 使用它的优点：

    （1）优化了属性的存储，直接减少了不必要的内存使用；

    （2）有属性变化通知、限制、验证等；

    （3）可以储存多个值，配合 Expression 及 Animation 等，打造出更灵活的使用方法。

【补充】

  • 依赖属性（Dependency Property）由 DependencyProperty 注册（DependencyProperty.Register），支持：
    • 属性值继承（如沿逻辑树继承 DataContext、FontSize）；
    • 数据绑定/样式/模板/动画/触发器统一接入属性系统；
    • 变更通知与验证回调（PropertyChangedCallback、ValidateValueCallback）；
    • 内存优化：未设置的属性不占用实例字段，默认值集中存储。
  • 定义示例：
public static readonly DependencyProperty TitleProperty =
    DependencyProperty.Register("Title", typeof(string), typeof(MyControl),
        new PropertyMetadata(string.Empty, OnTitleChanged));
public string Title
{
    get => (string)GetValue(TitleProperty);
    set => SetValue(TitleProperty, value);
}
  • 对比普通 CLR 属性：普通属性是"字段的包装"，无通知、无继承、无绑定能力；依赖属性专为 WPF 绑定/动画/样式体系设计。

28、Async/Await 定义异步方法的几点要求

定义一个异步方法应满足以下几点：

  1. 使用 async 关键字来修饰方法；
  2. 在异步方法中使用 await 关键字（不使用编译器会给出警告但不报错），否则异步方法会以同步方式执行；
  3. 尽量不使用 void 作为返回类型，若希望异步方法返回 void 类型，请使用 Task；
  4. 异步方法名称以 Async 结尾；
  5. 异步方法中不能声明使用 ref 或 out 关键字修饰的变量。

【补充】

  • 返回类型规则：
    • Task<TResult>：有返回值；
    • Task：无返回值；
    • void：仅限事件处理器（async void 的异常无法被外部捕获，会直接崩溃进程）；
    • C# 7+ 还可返回 ValueTask<T>（减少热路径上的分配）。
  • 命名约定：以 Async 结尾（如 LoadDataAsync）。
  • 补充限制：不能对 async 方法使用 ref/out 参数（编译器限制，原因：异步方法返回后栈帧可能已销毁）。
  • 常见面试追问：await 之后代码运行在哪个线程？（默认回到调用上下文的同步上下文，WPF 中即 UI 线程）；Task.Run 与 await 的区别（Task.Run 主动丢到线程池，await 是等待不阻塞）。
