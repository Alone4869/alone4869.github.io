一、虚方法和抽象方法的区别是什么

✅面试简答（考场口述答案）

虚方法（Virtual Method）和抽象方法（Abstract Method）都支持多态，但核心区别在于是否有默认实现以及对子类的强制力：

  1. 实现体：
    • 虚方法：有具体的方法体（实现逻辑）。子类可以选择重写（override），也可以直接继承使用基类的默认逻辑。
    • 抽象方法：没有方法体（只有签名）。子类必须重写（override）该方法，否则子类也必须声明为抽象类。
  2. 所属类：
    • 虚方法：可以存在于普通类或抽象类中。
    • 抽象方法：只能存在于抽象类（abstract class）中。
  3. 设计意图：
    • 虚方法：提供“默认行为”，允许子类按需扩展或修改（Template Method 模式常用）。
    • 抽象方法：定义“强制契约”，要求所有子类必须具备某种能力，但具体实现由子类决定。

📚深入解析

1. 语法与行为对比

特性 虚方法 (virtual) 抽象方法 (abstract)
关键字 virtual abstract
方法体 ✅ 必须有 { ... } ❌ 不能有 { ... }，以分号结尾
子类义务 可选重写 (override) 必须重写 (override)
所在类 普通类 或 抽象类 仅限 抽象类
访问修饰符 可以是 private (无意义), protected, public 等 不能是 private (因为子类必须能访问并重写)
性能 虚调用开销 (V-Table) 虚调用开销 (V-Table)，无额外差异

2. 代码示例 

// 抽象类
public abstract class Shape
{
    // 1. 抽象方法：强制子类实现计算面积的逻辑
    public abstract double CalculateArea();

    // 2. 虚方法：提供默认的显示逻辑，子类可以选择不重写
    public virtual void DisplayInfo()
    {
        Console.WriteLine($"This is a shape with area: {CalculateArea()}");
    }
}

public class Circle : Shape
{
    public double Radius { get; set; }

    // ✅ 必须实现抽象方法
    public override double CalculateArea()
    {
        return Math.PI * Radius * Radius;
    }

    // ⭕ 可选：如果不重写，直接继承 Shape 的 DisplayInfo
    // 如果想自定义显示方式，可以重写：
    public override void DisplayInfo()
    {
        Console.WriteLine($"Circle Area: {CalculateArea()}");
    }
}

3. 底层原理

  • 相同点：在 IL（中间语言）层面，两者都被标记为 virtual。这意味着它们在运行时都通过**虚方法表（V-Table）**进行动态绑定。
  • 不同点：抽象方法在元数据中被标记为 abstract，编译器会强制检查继承链，确保非抽象子类提供了实现。如果子类漏掉了抽象方法的重写，编译直接报错。

4. 设计模式中的应用

  • 模板方法模式（Template Method）：通常结合使用。
    • 基类定义一个算法骨架（普通方法或虚方法）。
    • 其中的某些步骤定义为抽象方法（强制子类实现核心差异）。
    • 另一些步骤定义为虚方法（提供默认钩子，子类可选覆盖）。

💡面试延伸追问（预判面试官后续提问）

  1. 抽象方法可以是 private 吗？
    • 考点：不可以。因为抽象方法的目的是让子类重写，private 成员对子类不可见，这会导致逻辑矛盾。编译器会报错。
  2. 虚方法可以是 private 吗？
    • 考点：语法上可以，但没有意义。因为 private 方法不能在类外部访问，子类也无法看到它，自然无法 override。所以 private virtual 实际上退化成了普通的 private 方法。
  3. 如果基类有一个虚方法，子类重写了它，孙类还能再重写吗？
    • 考点：可以。只要子类使用了 override，该方法在孙类眼中依然是一个虚方法，可以继续被 override。如果子类使用 new 隐藏了该方法，则断开了多态链，孙类无法再基于基类引用实现多态。
  4. 接口中的方法默认是抽象的吗？
    • 考点：在 C# 8.0 之前，接口方法隐式是 public abstract 的（不能有实现）。C# 8.0+ 引入了默认接口实现，此时接口方法可以有身体，但它不再是传统意义上的“抽象方法”，而更像是一种带有默认行为的虚方法（但不能包含状态）。

二、什么是方法重载

✅面试简答（考场口述答案）

方法重载（Method Overloading）是指在同一个类中，定义多个名称相同但参数列表不同的方法。

  • 核心规则：
    1. 方法名必须相同。
    2. 参数列表必须不同：参数的个数、类型或顺序至少有一项不同。
    3. 返回值类型可以不同，但不能仅靠返回值不同来区分重载。
  • 本质：属于编译时多态（静态多态）。编译器在编译阶段根据调用时传入的参数类型和数量，确定具体调用哪个方法。
  • 目的：提供统一的接口名称，简化调用者的记忆负担，提高代码可读性（例如 Console.WriteLine 可以打印 int, string, double 等）。

📚深入解析

1. 合法的重载示例 

public class Calculator
{
    // 1. 参数个数不同
    public int Add(int a, int b) { return a + b; }
    public int Add(int a, int b, int c) { return a + b + c; }

    // 2. 参数类型不同
    public double Add(double a, double b) { return a + b; }

    // 3. 参数顺序不同（通常不建议，易混淆）
    public void Process(string name, int id) { }
    public void Process(int id, string name) { }
}

2. 非法的重载（编译错误）

  • 仅返回值不同：

    public int GetId() { return 1; }
public string GetId() { return "1"; } // ❌ CS0111: 已经定义了具有相同参数类型的成员

    原因：调用 GetId() 时，编译器无法确定你想要哪个结果，除非你显式指定接收变量的类型，但这不符合 C# 的解析规则。

  • 仅参数名称不同：

    public void Show(int num) { }
public void Show(int count) { } // ❌ 参数名不影响签名

  • 仅 ref/out 修饰符不同：

    public void Test(int a) { }
public void Test(ref int a) { } // ❌ CS0663: 'ref' 和 'out' 不能用于区分重载

    注意：虽然 ref 和 out 本身不能区分，但如果一个有 ref 另一个没有，且类型不同，是可以的。但单纯 ref int vs int 是不行的，因为它们在元数据签名中被视为相同。(更正：实际上 ref 和 out 在签名中是有区别的，但 C# 规范规定不能仅凭 ref/out 或 params 来区分重载，除非结合其他差异。最典型的禁止是：void M(int a) 和 void M(ref int a) 是不能共存的)。

3. 编译器如何解析重载？

当你调用一个重载方法时，C# 编译器遵循以下优先级：

  1. 精确匹配：寻找参数类型完全一致的方法。
  2. 隐式转换匹配：如果没有精确匹配，寻找可以通过隐式转换（如 int -> long，int -> double）匹配的方法。
  3. 装箱匹配：如果还没找到，考虑将值类型装箱为 object 或接口。
  4. Params 匹配：最后考虑带有 params 数组的方法。

陷阱：如果有多个方法都可以通过隐式转换匹配，编译器可能会报“歧义调用”错误（CS0121）。

4. 重载 vs 重写（Overriding）

特性 重载 (Overloading) 重写 (Overriding)
范围 同一个类内部 基类与子类之间
多态类型 编译时多态（静态） 运行时多态（动态）
方法名 必须相同 必须相同
参数列表 必须不同 必须相同
返回值 可以不同 必须相同（或协变返回类型）
关键字 无特殊关键字 virtual, override

💡面试延伸追问（预判面试官后续提问）

  1. 构造函数可以重载吗？
    • 考点：可以。这是最常见的重载场景。通过提供不同参数的构造函数，方便调用者以不同方式初始化对象（如默认构造、全参构造、拷贝构造）。
  2. 为什么 C# 不允许仅通过返回值类型来区分重载？
    • 考点：因为在很多情况下，调用者会忽略返回值（如 obj.Method();）。如果此时有两个同名同参但返回值不同的方法，编译器无法判断该调用哪一个。此外，这也增加了语言解析的复杂性。
  3. 泛型方法可以重载吗？
    • 考点：可以。例如 void Do<T>(T item) 和 void Do(int item) 是合法的重载。编译器会根据类型推断优先匹配非泛型版本（如果存在精确匹配）。
  4. 什么是“隐藏”（Hiding）？它和重载有什么区别？
    • 考点：隐藏发生在父子类之间，子类定义了与基类同名同参的方法（使用 new 关键字）。重载发生在同类内部，参数列表不同。隐藏是静态绑定，重载也是静态绑定，但应用场景完全不同。

三、方法重写和方法隐藏的区别是什么

✅面试简答（考场口述答案）

方法重写（Overriding）和方法隐藏（Hiding/Shadowing）都涉及子类定义与基类同名的方法，但核心区别在于多态性和绑定机制：

  1. 多态性：
    • 重写 (override)：支持运行时多态。通过基类引用调用方法时，会根据对象的实际类型执行子类的方法。
    • 隐藏 (new)：不支持多态。通过基类引用调用方法时，始终执行基类的方法；只有通过子类引用调用时，才执行子类的方法。
  2. 关键字与前提：
    • 重写：基类方法必须标记为 virtual、abstract 或 override；子类使用 override。
    • 隐藏：基类方法可以是任何非虚方法；子类使用 new（如果不写，编译器会报警告，建议显式加上）。
  3. 绑定时间：
    • 重写：动态绑定（运行时决定）。
    • 隐藏：静态绑定（编译时根据变量声明类型决定）。

📚深入解析

1. 代码对比示例

这是面试中最经典的考点，请务必理解输出结果的原因。

public class Base
{
    public virtual void ShowVirtual() { Console.WriteLine("Base Virtual"); }
    public void ShowNormal() { Console.WriteLine("Base Normal"); }
}

public class Derived : Base
{
    // 1. 重写：替换基类的虚方法实现
    public override void ShowVirtual() { Console.WriteLine("Derived Override"); }

    // 2. 隐藏：定义一个新的同名方法，切断与基类的联系
    public new void ShowNormal() { Console.WriteLine("Derived New"); }
}

// 测试代码
Base b = new Derived(); // 基类引用指向子类对象
Derived d = new Derived(); // 子类引用指向子类对象

// === 重写行为 (多态) ===
b.ShowVirtual(); // 输出: "Derived Override" (看实际对象类型)
d.ShowVirtual(); // 输出: "Derived Override"

// === 隐藏行为 (非多态) ===
b.ShowNormal();  // 输出: "Base Normal"   (看变量声明类型 Base)
d.ShowNormal();  // 输出: "Derived New"    (看变量声明类型 Derived)

2. 底层原理：V-Table vs 静态解析

  • 重写 (override)：

    • 基类和子类的虚方法表（V-Table）中，该方法的槽位指向的是同一个最终实现（即子类的方法）。
    • 无论你把对象转换成什么基类接口，只要调用的是虚方法，CLR 都会去 V-Table 里找最新的那个地址。

  • 隐藏 (new)：

    • 这在内存中是两个完全独立的方法。
    • 编译器在编译 b.ShowNormal() 时，发现 b 的类型是 Base，于是直接生成调用 Base.ShowNormal() 的指令。它根本不在乎 b 实际上是不是 Derived 对象。

3. 为什么需要“隐藏”？

既然隐藏破坏了多态，为什么 C# 还允许它？主要为了版本控制兼容性：

  • 场景：你发布了一个库 Library v1.0，里面有个类 MyClass 没有 Process() 方法。用户继承 MyClass 写了自己的 Process()。
  • 升级：你在 Library v2.0 中给 MyClass 添加了一个新的 Process() 方法。
  • 问题：如果没有“隐藏”机制，用户的子类会因为突然多出一个同名方法而报错或行为不可控。
  • 解决：C# 允许用户的子类方法自动“隐藏”基类的新方法（虽然会报警告），保证用户的代码在升级库后依然能编译通过，且保持原有逻辑不变。

4. 最佳实践

  • 优先使用重写：在设计框架或基类时，如果希望子类能改变行为，务必将方法设为 virtual。
  • 谨慎使用隐藏：除非是为了处理第三方库的版本冲突，否则不要主动使用 new 来隐藏基类成员。这会使得代码逻辑变得晦涩难懂，违背面向对象的多态初衷。
  • 消除警告：如果你确实需要隐藏，请显式加上 new 关键字，告诉编译器“我是故意的”，从而消除 CS0108 警告。

💡面试延伸追问（预判面试官后续提问）

  1. 如果基类方法是 private，子类能重写或隐藏它吗？
    • 考点：
      • 不能重写：private 方法对子类不可见，无法 override。
      • 可以隐藏：子类可以定义一个同名的 public 方法，但这只是巧合的名字相同，两者没有任何关系，不属于严格意义上的“隐藏基类成员”，因为基类成员压根不在作用域内。
  2. override 可以改变方法的访问修饰符吗？
    • 考点：不可以。重写方法必须保持与基类虚方法相同的访问级别（如基类是 public virtual，子类必须是 public override）。
  3. 什么是“协变返回类型”（Covariant Return Types）？C# 支持吗？
    • 考点：指子类重写方法时，返回值类型可以是基类方法返回值类型的子类。C# 5.0+ 开始支持这一特性（主要针对泛型接口和委托，以及后来的记录类型等），但在普通类方法重写中，通常要求返回类型严格一致或使用兼容的类型。
  4. 如果在构造函数中调用虚方法，会发生什么？
    • 考点：这是一个经典陷阱。在基类构造函数中调用虚方法时，如果该方法被子类重写了，会调用子类的重写版本。但此时子类的字段可能还未初始化，导致空指针异常或逻辑错误。因此，严禁在构造函数中调用虚方法。

四、C# 是否支持多重继承

✅面试简答（考场口述答案）

C# 不支持类的多重继承，但支持接口的多重实现。

  • 类（Class）：只能继承一个基类（单继承）。这是为了避免“菱形继承问题”（Diamond Problem）带来的状态冲突和内存布局复杂性。
  • 接口（Interface）：可以实现多个接口。因为接口只定义行为契约，不包含实例字段（状态），所以不存在内存布局冲突。
  • 替代方案：如果需要复用多个类的功能，应使用组合（Composition）、接口 + 默认实现（C# 8.0+）或Mixin 模式。

📚深入解析

1. 为什么禁止类的多重继承？

核心原因是菱形继承问题（Diamond Problem）：

      A
     / \
    B   C
     \ /
      D

如果 B 和 C 都继承自 A，且都重写了 A.Method()，那么当 D 继承 B 和 C 时：

  • D 应该调用哪个版本的 Method()？
  • A 中的字段应该在 D 的内存中存在一份还是两份？

C++ 通过虚继承等复杂机制解决了这个问题，但代价是语法复杂、性能开销大。C# 设计者认为这种复杂性得不偿失，因此选择了单继承 + 多接口的模型，既保证了安全性，又提供了足够的灵活性。

2. 接口多重实现的安全性

接口不包含实例字段（C# 8.0+ 的静态字段除外），只包含方法签名。因此：

  • 没有状态冲突：多个接口不会争夺同一块内存。
  • 没有构造函数链问题：接口没有构造函数。
  • 编译器可以简单地合并多个接口的方法分发表。
public interface IFlyable { void Fly(); }
public interface ISwimmable { void Swim(); }

// ✅ 合法：同时具备飞行和游泳能力
public class Duck : Animal, IFlyable, ISwimmable 
{
    public void Fly() { ... }
    public void Swim() { ... }
}

3. C# 8.0+ 默认接口实现的局限

虽然 C# 8.0 允许接口包含方法体（Default Interface Methods），但它依然不能拥有实例字段。这意味着：

  • 默认实现不能依赖对象状态。
  • 它不是真正的“多重继承”，而是一种“带默认行为的契约”。
  • 如果两个接口有同名默认方法且类未显式实现，会产生歧义，必须通过显式接口实现来解决。

4. 如何实现类似多重继承的效果？

方案 适用场景 示例
组合 (Composition) 需要复用多个类的完整功能 class Car { Engine engine; Wheel[] wheels; }
接口 + 扩展方法 为多个不相关类添加相同行为 static void Log(this ILogger logger, ...)
Mixin 模式 模拟多重继承的行为组合 通过接口 + 默认实现 + 辅助类实现
Source Generators 编译时代码生成，自动注入 boilerplate 代码 .NET 6+ 高性能场景

💡面试延伸追问（预判面试官后续提问）

  1. 什么是菱形继承问题？C++ 是如何解决的？
    • 考点：对比语言设计哲学。C++ 使用虚继承（virtual inheritance）确保基类子对象只存在一份，但这增加了对象大小和构造复杂度。C# 直接规避了这个问题。
  2. 如果一个类实现了两个接口，且这两个接口有同名的默认方法，会发生什么？
    • 考点：编译器会报错（CS8705），要求类必须显式实现该方法以消除歧义。这证明了默认接口实现并非无缝的多重继承。
  3. 为什么 C# 选择“组合优于继承”作为设计原则？
    • 考点：继承导致强耦合，基类修改可能破坏所有子类（脆弱基类问题）。组合通过委托实现功能复用，更灵活、更易测试、更符合开闭原则。
  4. 抽象类可以实现接口吗？如果可以，它必须实现接口的所有成员吗？
    • 考点：可以。抽象类可以选择性地实现接口成员，未实现的成员会自动成为抽象类的抽象成员，由具体子类负责实现。这提供了一种“部分实现接口”的模板机制。

五、为什么使用goto关键字被认为是不良实践

✅面试简答（考场口述答案）

在 C# 和现代软件开发中，goto 被认为是不佳实践，主要原因是它破坏了结构化编程的原则，导致代码出现“面条式代码”（Spaghetti Code）。

  1. 可读性差：goto 允许程序流随意跳转，使得逻辑执行顺序变得非线性且难以追踪，增加了阅读和维护代码的难度。
  2. 维护困难：随着代码量增加，随意的跳转会引入复杂的依赖关系，修改一处逻辑可能导致意想不到的副作用，极易引入 Bug。
  3. 有更好的替代方案：C# 提供了丰富的结构化控制流语句（如 if-else, for, while, break, continue, return, try-catch），这些语句能更清晰、更安全地表达相同的逻辑。

例外情况：在极少数性能极度敏感的场景或深层嵌套循环退出时，部分开发者可能会谨慎使用 goto，但这通常被视为一种“妥协”而非推荐做法。

📚深入解析

1. 历史背景与结构化编程

  • Dijkstra 的批评：1968年，计算机科学家 Edsger Dijkstra 发表了著名论文《Go To Statement Considered Harmful》，指出 goto 会导致程序逻辑混乱，难以进行形式化验证和调试。
  • 结构化编程：现代编程语言（包括 C#）都遵循结构化编程范式，强调使用顺序、选择（分支）和循环这三种基本结构来构建程序。goto 打破了这种清晰的层次结构。

2. C# 中 goto 的具体危害

  • 破坏局部推理：在阅读一段代码时，如果存在 goto，你无法仅通过当前作用域确定下一步执行哪里，必须全局搜索标签（Label）。
  • 绕过初始化：虽然 C# 编译器会阻止 goto 跳过变量初始化，但在复杂逻辑中，它仍可能绕过某些预期的清理逻辑或状态更新。
  • 干扰异常处理：goto 不能跳出 try 块进入 catch 或 finally 块，也不能从 catch 块外跳入。这种限制虽然保护了安全性，但也说明了它与 C# 核心机制的不兼容性。

3. 常见的替代方案

goto 场景 推荐的替代方案
跳出多层循环 提取方法（Extract Method），使用 return；或使用标志位配合 break。
错误处理/跳转 使用 try-catch-finally 进行异常处理。
状态机切换 使用 switch-case 或状态模式（State Pattern）。
重复代码块 提取为私有方法，通过方法调用来复用逻辑。

4. C# 中 goto 的合法但受限的使用场景

尽管不推荐，但 C# 依然保留了 goto，主要用于：

  • Switch 穿透：在 switch 语句中，从一个 case 跳转到另一个 case（goto case label;）或默认情况（goto default;）。这是 C# 明确支持且相对安全的用法。
  • 深层嵌套退出：在极其复杂的算法或生成的代码中，有时用 goto 退出多层嵌套比设置多个标志位更直观（但仍建议优先重构代码）。
// 相对可接受的 goto 用法：switch 穿透
switch (value)
{
    case 1:
        DoSomething();
        goto case 2; // 明确跳转到 case 2
    case 2:
        DoSomethingElse();
        break;
}

💡面试延伸追问（预判面试官后续提问）

  1. 如果在深层嵌套循环中需要立即退出，除了 goto 还有什么优雅的方法？
    • 考点：
      1. 提取方法：将嵌套循环封装成一个独立的方法，使用 return 直接退出。这是最推荐的重构方式。
      2. 标志位：设置一个 bool shouldExit 变量，在内层循环修改它，外层循环检查它并 break。
      3. 异常：极端情况下抛出自定义异常（不推荐用于流程控制，性能开销大且语义不符）。
  2. C# 编译器对 goto 有哪些限制？
    • 考点：
      1. 不能跳出类、方法或属性。
      2. 不能跳进 try 块的内部（除非从同一 try 块的另一处跳入）。
      3. 不能跳过变量的初始化（编译器会报错 CS0165）。
      4. 标签必须在当前方法内可见。
  3. 为什么 C 语言中 goto 的使用比 C# 中更常见？
    • 考点：C 语言缺乏异常处理机制和完善的资源管理（如 RAII），在错误处理和资源清理时，goto 常被用作一种集中清理资源的模式（如 Linux 内核代码）。而 C# 有 try-finally 和 using，完全不需要这种模式。
  4. 什么是“面条式代码”（Spaghetti Code）？
    • 考点：指控制流复杂、混乱、难以理解的代码，通常由过度使用 goto 或缺乏模块化设计导致。它是软件维护的噩梦。

六、SOLID中的S、O、L、I、D分别是什么

✅面试简答（考场口述答案）

SOLID 是面向对象设计的五大核心原则：

  1. S (Single Responsibility)：单一职责，一个类只负责一项职责。
  2. O (Open/Closed)：开闭原则，对扩展开放，对修改关闭。
  3. L (Liskov Substitution)：里氏替换，子类必须能替换父类而不改变程序正确性。
  4. I (Interface Segregation)：接口隔离，客户端不应依赖它不需要的接口。
  5. D (Dependency Inversion)：依赖倒置，高层模块不应依赖低层模块，二者都应依赖抽象。

📚深入解析与 C# 示例

1. S - 单一职责原则 (SRP)

定义：一个类应该只有一个引起它变化的原因。 反例：一个 UserService 既负责用户数据校验，又负责发送注册邮件，还负责写日志。 正例：拆分为 UserValidator、EmailService、Logger。

// ❌ 违反 SRP
public class UserService
{
    public void Register(string email) { /* 校验逻辑 */ /* 发邮件逻辑 */ /* 存库逻辑 */ }
}

// ✅ 符合 SRP
public class UserValidator { public bool IsValid(string email) => ...; }
public class EmailService { public void SendWelcomeEmail(string email) => ...; }
public class UserRepository { public void Save(User user) => ...; }

2. O - 开闭原则 (OCP)

定义：软件实体应当对扩展开放，对修改关闭。 场景：计算不同形状的面积。 反例：在 AreaCalculator 中使用 if (shape is Circle) ... else if (shape is Rectangle)。新增三角形需修改该类。 正例：定义 IShape 接口，每个形状实现自己的 GetArea()。

public interface IShape { double GetArea(); }
public class Circle : IShape { public double GetArea() => Math.PI * R * R; }
public class Rectangle : IShape { public double GetArea() => W * H; }
// 新增 Triangle 只需新建类，无需修改 AreaCalculator

3. L - 里氏替换原则 (LSP)

定义：子类对象能够替换程序中父类对象出现的任何地方，并且保证原来程序的逻辑行为不变。 经典反例：正方形继承矩形。矩形有 SetWidth 和 SetHeight，但正方形设置宽时高也要变，替换后会破坏原有逻辑。 正例：正方形和矩形都继承自更抽象的 Shape，而不是互相继承。

// ❌ 违反 LSP
public class Rectangle { public virtual int Width { get; set; } public virtual int Height { get; set; } }
public class Square : Rectangle 
{ 
    public override int Width { set { base.Width = value; base.Height = value; } } 
    // 如果客户端调用 rect.Height = 5; rect.Width = 10; 期望面积是50，但 Square 会导致面积变成100
}

4. I - 接口隔离原则 (ISP)

定义：客户端不应该依赖它不需要的接口。 场景：多功能打印机。 反例：定义一个大接口 IMachine 包含 Print, Scan, Fax。普通打印机不需要 Fax，但被迫实现。 正例：拆分为 IPrinter, IScanner, IFax。

// ✅ 符合 ISP
public interface IPrinter { void Print(); }
public interface IScanner { void Scan(); }

public class SimplePrinter : IPrinter { public void Print() { ... } } // 不需要实现 Scan
public class MultiFunctionDevice : IPrinter, IScanner { ... }

5. D - 依赖倒置原则 (DIP)

定义：高层模块不应该依赖低层模块，两者都应该依赖其抽象；抽象不应该依赖细节，细节应该依赖抽象。 场景：订单服务调用通知服务。 反例：OrderService 内部直接 new EmailNotifier()。 正例：OrderService 依赖 INotifier 接口，通过构造函数注入具体实现。

public interface INotifier { void Send(string message); }
public class EmailNotifier : INotifier { public void Send(string msg) => ...; }

public class OrderService
{
    private readonly INotifier _notifier;
    public OrderService(INotifier notifier) // 依赖抽象
    {
        _notifier = notifier;
    }
}

💡面试延伸追问（预判面试官后续提问）

  1. 这五个原则中，你认为哪个最重要？为什么？

    没有绝对的最重要，但依赖倒置 (DIP) 和 开闭原则 (OCP) 在现代架构（如微服务、插件化系统）中尤为关键，因为它们直接决定了系统的可维护性和可扩展性。

  2. 里氏替换原则 (LSP) 违反时，通常会出现什么症状？

    子类中抛出 NotSupportedException；子类重写方法时做了额外的类型检查；或者子类重写了父类方法但改变了其行为语义（如父类是加法，子类变成减法）。

  3. 接口隔离原则 (ISP) 在 C# 中如何具体落地？

    1. 定义小接口；2. 使用默认接口方法（C# 8.0+）提供可选实现；3. 使用适配器模式将大接口适配为小接口供特定客户端使用。

  4. 依赖倒置 (DIP) 和控制反转 (IoC) 是什么关系？

    DIP 是设计原则，指导我们要依赖抽象；IoC 是设计模式/技术手段，用于实现 DIP（如通过 DI 容器将具体实现注入给抽象）。DIP 是思想，IoC 是工具。

  5. 在实际项目中，如何平衡 SOLID 原则和开发效率？

    不要过度设计。对于简单且变动小的模块，可以直接编写；对于核心业务、易变模块，严格遵循 SOLID。通常 SRP 和 DIP 是最容易落地且收益最高的。

  6. 里氏替换原则（LSP）在 C# 中如何通过代码约束来保证？

    尽量使用 abstract 类或接口定义契约；避免在子类中抛出父类未声明的异常；避免在子类中加强前置条件或减弱后置条件。

  7. 接口隔离原则（ISP）在 C# 8.0+ 有了默认接口方法后，是否还重要？

    依然重要。虽然默认方法减少了实现负担，但从语义上讲，将不相关的功能拆分到不同接口仍有助于保持接口的内聚性和清晰度，方便 Mock 测试。
